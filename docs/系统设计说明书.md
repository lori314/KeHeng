# 科衡系统设计说明书

## 1. 设计目标

本设计描述科衡的候选总体架构、模块职责、核心流程和关键质量属性，为后续技术选型和详细设计提供基线。当前不绑定具体编程语言、模型供应商、向量数据库或部署平台。

系统设计优先满足：端到端可运行、证据可追溯、模块可替换、任务可恢复、权限可隔离和操作可审计。性能与智能效果优化应建立在可测量基线之上。

Iteration 05 产品流程沿用统一分析服务。真实模型 Agent 使用最多 4 个查询、每查询 top-3；上下文按查询组轮转组装，最多 8 个完整句段、4,160 字符。字符预算不等价于 token 预算。provider request history 是实际发送片段的核验依据；检索候选召回不能替代送入模型上下文核验。历史报告回放固定读取本机已保存结果，不触发模型调用。

## 2. 架构原则

- 业务编排与模型调用分离，避免模型供应商逻辑侵入领域层。
- 原始资料、派生内容、检索索引、分析结论和报告分别管理并建立血缘。
- Agent 通过明确输入输出契约协作，不共享隐式记忆或直接修改他方状态。
- 所有结论均携带证据引用和生成上下文；证据不足可返回未决状态。
- 同步交互与长时任务分离，长任务使用可恢复的状态机或工作流编排。
- 正式配置不可原地修改，采用版本、生效范围和审批状态管理。

## 3. 系统上下文

系统主要与尽调人员、专业复核人员、审批/风控人员、管理员和审计人员交互。潜在外部依赖包括组织身份源、对象存储、模型服务、文档解析组件以及经授权的数据源。这些依赖均应通过适配接口接入，并在设计评审中确认安全边界、成本和降级策略。

高层数据流为：

```text
用户/机构资料
      ↓
任务与资料管理 → 安全检查/解析 → 企业知识空间
      ↓                            ↓
业务工作流编排 ← 专项 Agent ← 证据检索
      ↓
指标评价 → 报告汇总 → 人工复核/审批 → 版本化输出
      ↘ 全链路元数据、监控与审计 ↙
```

## 4. 逻辑模块

### 4.1 前端 `frontend/`

承载任务创建、资料状态、分析进度、证据阅读、评分解释、报告编辑和审批交互。前端只展示后端授权的数据，不保存核心业务规则，不在客户端计算正式评分。

### 4.2 后端 `backend/`

承载认证授权接入、任务与资料元数据、业务 API、工作流编排、配置生效、报告版本和审计事件。后端是用户动作与领域能力之间的边界，不直接耦合具体模型 SDK 或向量库查询语法。

### 4.3 专项智能体 `agents/`

- `technology_agent/`：技术创新性、成熟度、知识产权和研发工程化分析。
- `industry_agent/`：市场、竞争、产业链、政策和商业化分析。
- `finance_agent/`：财务质量、现金流、融资与异常勾稽分析。
- `report_agent/`：整合已形成的结构化分析与评价，不负责创造缺失事实。

每个 Agent 后续应定义目标、允许工具、输入模式、输出模式、证据最小要求、拒答条件、超时、重试和评测集。跨 Agent 冲突由编排层显式记录并交由复核规则处理。

### 4.4 RAG `rag/`

- `document_parser/`：文件识别、安全检查、解析、版面/结构保留及质量报告。
- `embedding/`：分块和向量表示适配，记录模型、版本和处理参数。
- `retrieval/`：权限过滤、查询改写、混合检索、重排和结果封装。
- `knowledge_base/`：企业/任务知识空间、索引生命周期、版本和血缘管理。

RAG 输出应至少包含内容片段、资料标识、位置、时间、权限上下文、检索分数和处理版本。

### 4.5 评价 `evaluation/`

集中管理指标、权重、尺度、阈值、缺失值和风险处理逻辑，输出维度得分、总览、证据、解释、不确定性和配置版本。评价模块不得将模型生成的自由文本直接当作无验证数值输入。

v0.3 的最小实现位于根目录 `evaluation/`：Technology Agent 通过结构化契约提供四项带证据指标，评价引擎读取版本化指标及固定权重配置，校验取值范围、权重合计和证据引用后执行加权计算。该实现通过权重提供器接口保留 AHP 扩展空间，不改变既有 FastAPI 接口边界。

### 4.6 数据、配置、脚本与测试

`data/` 仅保存可提交的脱敏/合成样本；`configs/` 保存无秘密的模板；`scripts/` 保存可复用工程操作；`tests/` 提供跨模块质量验证。这些目录在相应方案评审前保持技术中立。

### 4.7 报告生成与展示

v0.4 报告生成器位于 `backend/app/report/`，输入为已形成的 Technology Agent 和 Evaluation Engine 结构化结果。生成器只执行字段装配与引用完整性校验，不重新计算评分、不新增分析结论。FastAPI 继续通过 `POST /report/generate` 暴露同步转换接口。

v0.5 在 `backend/app/services/` 增加统一技术评估应用服务，依次编排 PDF 解析、任务独立 Chroma 知识库、Technology Agent、Evaluation Engine 和 Report Generator。`POST /analysis/create` 接收企业名称与文本型 PDF 并返回任务编号，`GET /analysis/{task_id}` 返回 `processing`、`completed` 或 `failed`；完成状态携带统一报告。任务状态为单进程内存实现，知识库存储按任务目录物理隔离并继续执行 `task_id` 过滤。React 页面通过上传和轮询动态展示报告，静态报告仅作为明确标注的内置虚构样例。

v0.6 在同一编排边界内加入可替换 LLM 抽取层：Provider 接口、OpenAI-compatible 适配器和离线 Mock 分离，Agent 通过配置选择 `rule`/`llm`/`fallback`。LLM 仅处理已检索证据片段，评分仍由根目录 Evaluation Engine 完成；提示词、Provider 响应和 E 编号校验均属于抽取阶段，不改变报告或评价接口。

### 4.8 Iteration 03 产品入口状态

`POST /analysis/create` 与离线配对实验均调用 `TechnologyAssessmentService.run_product`。上传表单显式选择 `rule_demo`（仅技术规则分析）或 `real_model`（技术与产业模型模块及综合评价）；后端模型配置缺失时失败并提示，不作模式回退。任务响应分别保存技术/产业模块状态、失败原因、请求/实际模式、输入 PDF 哈希、检索和评分配置指纹；真实模型传输另外保存最终请求上下文、原始响应和请求观测。当前任务状态仍为单进程内存实现，真实模型原文仅随该任务查询响应返回。

检索依赖相同知识库接口，`hash` 保持现有字符 n-gram baseline；`bm25` 为配置候选，使用共享 NFKC/拉丁词/CJK 重叠二元组实现和通用双语指标 query 定义。BM25 与 hash 均在请求 `task_id` 过滤后检索。前端展示模块状态、分母明确的指标覆盖、证据定位及补材料建议；未确认的离线候选不显示为模型或人工 gold。

v0.7 保留上述技术服务和 API 契约，新增 `IndustryAgent` 与 opt-in `run_comprehensive` 编排路径。Industry Agent 从同一任务知识库提取市场潜力、行业成长性、竞争位置和政策环境四项带 E 编号的观察；`evaluation/industry/` 使用独立固定权重计算产业分，`evaluation/composite_weights.yaml` 以技术 60%、产业 40% 组合维度分。`ComprehensiveReportGenerator` 在不改变原 `TechnologyReport` 契约的前提下增加产业价值分析章节、产业优势/风险及综合分。

v0.9 在原 Provider 边界内增加标准库 HTTP transport，面向百炼 OpenAI Compatible `/chat/completions` 和 `/models` 接口。transport 只保存内存中的密钥和本次响应，不把认证信息写入运行产物；模型、端点、温度和提示词版本通过实验配置记录。`evaluation/run_v09_experiments.py` 对三个技术合成案例和三个技术+产业案例执行 rule 基线与 LLM 重复运行，`evaluation/run_real_cases.py` 对 `data/real_cases/` 中有合法来源的企业资料执行真实 `llm` 综合流程。真实企业输出不设金标准，单独保存分析、评价、报告和运行状态；失败不降级、不伪造结果。

v1.0 保持模块化单体结构，Provider 对 timeout、429、5xx 和临时连接错误进行最多两次退避重试，并记录调用观测；JSON/schema/evidence 错误不重试、不补全。Technology 与 Industry 可分别显式配置 `rule`/`llm`，综合服务仍由同一编排入口调用。综合评价输出证据覆盖率和 assessment status；`insufficient_evidence` 时 `overall_score` 为 null，`pipeline_failed` 与资料不足分离。v1.0 实验脚本写入 `runtime/experiments/v10/`，真实案例状态和人工复核待填表写入 `runtime/real_cases/` 与 `data/real_cases/human_review_v10.csv`。

v1.1 Iteration 02 为实验与演示 runner 增加独立新建 run 目录和 provenance 记录。指定的输出目录若已存在即报错；真实案例人工复核模板写入 run 内的 `human_review_suggestions.csv`，人工标签 CSV 不由实验过程重置。默认技术 demo 仍可无参数运行，但输出改为 `runtime/demo_runs/run-*`。`evaluation/recompute_history.py` 对旧 raw 离线复算，`evaluation/run_retrieval_comparison.py` 仅比较本地向量、BM25 与 RRF，不接入产品检索链路，也不调用模型。

## 6. 关键流程设计

### 6.1 资料摄取

资料进入隔离区后完成格式和安全检查；计算内容指纹并登记授权与元数据；解析器产生结构化内容和质量报告；合格内容分块并建立索引。任何失败都形成可见状态，原始资料与派生结果通过版本关联。

### 6.2 分析与评价

编排层冻结本次运行的数据、检索、模型、提示词和评价配置版本；按主题调用 Agent；Agent 仅使用已授权证据并返回结构化发现；冲突或低置信结果进入复核队列；评价模块基于有效输入形成解释性结果。

### 6.3 报告与审批

报告模块使用专项发现和评价结果生成草稿；引用校验器检查每项关键结论；用户修订时保留差异与责任人；满足审批规则后冻结报告版本。已发布版本不可原地覆盖，需通过新版本更正。

## 7. 接口与契约原则

- 接口采用版本化的结构化消息，明确必填项、枚举、错误码和幂等键。
- 长任务返回任务标识和状态，不以超长同步请求维持连接。
- v0.5 分析接口使用 `multipart/form-data` 创建任务；非 PDF、空文件、伪 PDF 在创建阶段拒绝，损坏 PDF 和无文本 PDF 进入 `failed` 并返回稳定错误码。
- 错误区分可重试、不可重试、权限拒绝、输入无效、证据不足和人工处理。
- 引用使用稳定资料标识和位置坐标，不只保存容易漂移的文本内容。
- 外部模型、解析器、向量库和数据源均置于适配器之后，支持超时、限流、熔断与替换。

具体 API 和事件模式将在技术选型后以独立接口文档或机器可读契约补充。

## 8. 安全与权限设计

按组织、项目/任务、角色、资料密级进行授权，检索前过滤与结果返回时复核并用。原始文件与索引采用一致的权限域。提示词和检索内容视为不可信输入，防范指令注入、数据外带和工具越权。关键配置变更、资料访问、报告导出和审批写入审计链路。密钥使用专门秘密管理能力，不进入仓库、镜像或日志。

## 9. 可靠性与可观测性

每次运行使用全链路关联标识；记录阶段状态、耗时、资源、模型与配置版本、检索质量和失败类型。工作流步骤应幂等，支持断点恢复和受控重试。模型或检索不可用时明确降级，不以空数据生成看似完整的结果。备份、恢复点和恢复时间目标待部署约束确认。

## 10. 部署构想

首期可按模块化单体加异步工作进程建设，以降低分布式复杂度；仅当团队规模、负载或隔离需求有证据时拆分服务。开发、测试和生产环境隔离。具体采用本地化、专有云或混合部署，需依据机构网络、数据驻留和模型访问政策决定。

## 11. 关键待决策项

- 应用技术栈、工作流框架及任务队列。
- 文件/对象存储、结构化数据库、搜索与向量存储方案。
- 文档解析与 OCR 能力边界、首期支持格式。
- 模型部署形态、供应商适配、上下文与成本预算。
- 身份源、权限模型、审计保留和加密要求。
- 模块化单体与服务拆分的演进触发条件。

## v1.1 Provider 运行语义

模型适配器支持可关闭的 JSON mode，并在结构化契约失败时执行一次格式修复。修复请求复用原检索证据，仅附加上一轮输出和格式约束；不重新进行事实分析、不调用 rule、不改变 Evaluation 或 Report。

## V2 Knowledge Contract（第一、二阶段）

`backend/app/knowledge/` 定义与存储和检索供应商无关的 Company、Source、SourceVersion、Citation、CitationLocator 和 KnowledgeChunk 契约。Source 表示逻辑出处；SourceVersion 表示经过内容 hash 确定的来源快照；Citation 表示其带摘录与位置的引用；KnowledgeChunk 是共享检索的最小知识单元。`canonical_url` / `source_url` 在 Source、Citation 与网页 locator 间保留。第三阶段通过独立研究模块实现网页搜索、正文提取和入库，旧分析链路仍未迁移。

`task_id` 只描述当前任务上下文，不是长期知识身份。`E1/E2` 仍是一次 Agent 输入中的临时引用标签，长期溯源由 `citation_id`、`source_id` 和 locator 表达。知识层预留 enterprise、domain、lifecycle、standard、regulation、financial_rule 和 general，领域/模板标签暂保持开放字符串。

第二阶段新增 `backend/app/knowledge/identity.py`、`repository.py` 和 `shared_knowledge_base.py`。来源以 external_id、规范 URL 或上传 PDF 内容 SHA-256 标识；source version 以 source_id + 内容 SHA-256 标识；chunk/citation 以版本、定位器和规范化原文标识。`SourceVersion` 与完整 chunk/citation 由 SQLite 持久化并保留历史；专用 Chroma collection `keheng_shared_knowledge_v2` 作为当前版本向量索引，metadata filter 可限定 company、knowledge layer 和 source type。搜索返回前以 SQLite 校验 current version，并还原完整来源与证据元数据。默认目录为 `runtime/knowledge/`，默认 embedding 是可替换的本地 hashing baseline，不代表已选定生产 embedding。

## V2 第六阶段：企业身份解析与来源准入

`backend/app/research/orchestrator.py` 现在先执行最多 4 个、每个最多 5 条结果的主体身份检索，再进入企业技术/经营等深度检索。`IdentityResolver` 只接受本轮检索结果中的证据 URL，并校验名称、别名、官网和统一社会信用代码是否能从所引用结果中核验。主体歧义或未解析时流程停止，不执行深度检索，也不将身份搜索结果写入知识库；解析成功时更新同一 `Company` 记录并保存解析证据 URL。

主体解析成功后，所有搜索页先经 `EnterpriseRelevanceGate`：官网 host 及其子域名走确定性准入，其余页面由结构化模型标记为 relevant、irrelevant 或 uncertain。仅 relevant 页面进入 `Source → SourceVersion → KnowledgeChunk/Citation`；三个状态及来源类型数量写入迭代结果和轮次 trace。`backend/app/research/source_classifier.py` 使用 `configs/research/source_host_registry.yaml` 和搜索 topic 分类政府、监管、登记、专利、论文、新闻、企业官网或一般网页。该实现尚未改变知识库隔离模型，也没有网页之外的来源连接器。

`backend/app/knowledge/adapters.py` 将当前 ParsedDocument/DocumentChunk 映射为带 PDF 页码、原 locator、摘录、source version 和稳定 V2 chunk ID 的对象，同时保留 `legacy_chunk_id` 及任务上下文供兼容排查。旧 `ChromaKnowledgeBase`、BM25KnowledgeBase、RetrievedEvidence、Agent Evidence、ReportEvidence 和既有 PDF → RAG → Evaluation → Report 执行链路仍保持原状；共享知识库是新建的独立能力，尚未替换旧分析流程。第二阶段没有知识更新 UI、联网检索或网页抓取；第三阶段已增加仅供 CLI 使用的搜索与网页抓取链路，但仍无增量文件监控、权限模型或知识更新界面，权限继承与索引治理仍待后续设计。

## V2 第三阶段：迭代式外部研究

`backend/app/research/` 提供独立的 `RetrievalPlanner`、provider-neutral `WebSearchProvider`、Tavily adapter、网页内容分块与 `IterativeResearchService`。第一轮计划按企业身份、业务、技术、产品、人员分组；后续 planner 收到已执行 query、当轮标题/搜索摘要、已验证发现词和缺口。程序只接受出现在该轮实际搜索标题/摘要/正文中的发现词作为后续 query 锚点，并要求 follow-up query 同时包含企业名与该锚点。Planner 不进行企业价值判断。

编排使用有界并发搜索、query/URL 去重、最多一次结构修复及配置化的来源数、无增益轮次限制；默认最多 3 轮、每轮 6 个 query、每个 query 5 个搜索结果、每次研究最多 25 个唯一 URL。trace 保存每轮 query、命中数、重复 URL、新词、缺口、规划理由、正文提取失败类别和停止原因。Tavily 使用标准库 HTTP；凭据从 `KEHENG_TAVILY_API_KEY` 读取，模型沿用现有 `KEHENG_LLM_ENDPOINT` / `KEHENG_LLM_MODEL` / `KEHENG_LLM_API_KEY` 配置。只在 CLI `scripts/run_iterative_research.py` 显式执行时联网，研究 JSON trace 写入被 Git 忽略的 `runtime/research/`。

Search 原文不足时尝试 Tavily Extract。若仍只有摘要，写入的 SourceVersion 与 KnowledgeChunk 标记 `content_scope=search_snippet`，不与完整正文等同。网页按标题、段落边界分块，Citation 保存规范 URL、heading/section、paragraph number 和 text anchor，随后写入现有 SQLite + Shared Chroma。网站来源默认标为 `web`；仅 `.gov` / `.gov.cn` 域名和新闻 topic 使用相应来源类型，不推断企业官网归属。

截至第三阶段，旧 analysis pipeline、报告与前端没有迁移，当时也没有行业模板、生命周期判断、金融推理、Chat、正式知识更新 UI 或外部搜索任务 API。外部服务数据流为：搜索 query 发送给 Tavily，必要时将所选 URL 发送 Tavily Extract；Planner LLM 接收企业名、已执行 query、来源标题/搜索摘要、已验证发现词和缺口，不接收完整抓取正文。API Key 不写入 trace、任务结果、SQLite 或日志。未配置任一必需 provider 时 CLI 明确返回 `provider_not_configured`，不会改用 fake 数据。

### V2 第四阶段：自适应科技知识语义加工

`backend/app/knowledge/semantic/` 依赖统一知识契约、SQLite/SharedKnowledgeBase 和通用 `backend/app/llm/` 结构化模型边界，不依赖 `research/` 内部实现。入口 `TechnologyKnowledgeProcessor.process_company(company_id)` 只读取该企业当前 `GENERAL` chunks，依次调用 domain/template classifier、technology fact extractor 和 technology interpreter；三个步骤分别使用独立 prompt、结构化契约和最多一次格式修复。真实调用通过 `scripts/run_technology_semantic_processing.py` 显式触发，不增加正式 API/UI。

领域 taxonomy 由 `configs/knowledge/domain_registry.yaml` 版本化，登记《战略性新兴产业分类（2018）》九个顶层领域的代码与名称；六个可组合研发/产业化模板位于 `technology_templates.yaml`。LLM 只能从两份 registry 的 ID 中选择，且所有选择需绑定本次输入 chunk。模板包含研发对象、milestone、证据类型、检索提示和项目自有允许/禁止推断规则。`standard_references.yaml` 只登记 GB/T 37264-2018、GB/T 40518-2021、ISO 16290:2013 的书目信息及边界说明；标准 reference metadata 不是标准原文，不会作为标准 citation 或条文知识使用。

原始 GENERAL 内容保持不覆盖。单来源 `TechnologyFact` 由代码校验 `source_chunk_id`，Citation 从原始 chunk 复制，不接受模型生成 Citation；fact ID 基于 company、原 chunk、原子字段和 processor/template 版本确定。派生事实写为新的 `ENTERPRISE` 或 `LIFECYCLE` chunk，继续引用相同 SourceVersion/Citation，并在 metadata 标注 `semantic_kind=technology_fact`、`derived_from_chunk_id`、`fact_id` 与 `processor_version`。共享知识检索可检索这些派生 chunk 并还原原 URL、标题、摘录和 locator。

Interpreter 只产生定性的 `MilestoneObservation`。请求按事实输入顺序分配短引用 `F1...Fn`，模型收到 compact fact view，不暴露内部 fact ID 或 Citation/provenance；应用只接受本次请求存在的短引用并映射回稳定 fact ID。非法引用按 observation fail-closed，合法部分可保留并降为 `limited_support`；短引用重复稳定去重，support/contradict overlap 被移除并降级。未知 template/milestone 和重复 observation 仍严格失败。Profile 同时保存 `InterpreterReport` 的引用质量与降级计数。模板确定性规则追加 `blocked_inferences` 并过滤命中禁止标记的强结论；例如芯片流片 fact 可以支持“观察到流片”，不能据此推出量产、稳定良率或客户采购。搜索 snippet 的来源类别固定为 `snippet_only`；若 observation 的支持事实仅为 snippet/weak web，`supported` 会被降为 `limited_support`。Profile 以带版本的 JSON 写入 SQLite，原子事实另写入 SharedKnowledgeBase；该阶段无技术综合分数、金融映射、授信判断，也不接回旧 Evaluation Engine。

显式运行语义 CLI 时，配置的 LLM provider 会接收企业名、registry、当前 GENERAL 正文/Citation 和前序结构化事实，用于三个分离阶段；语义 profile 的 JSON 副本写入被 Git 忽略的 `runtime/technology_semantic/`。它们是企业资料与敏感派生数据，应按部署的数据出域和保留策略管理。未配置 LLM 时命令在发出请求前返回 `provider_not_configured`。

Processor 使用两阶段 evidence selection。`backend/app/knowledge/semantic/evidence_selector.py` 的既有 `select_semantic_evidence` 先从所有 GENERAL chunks 中按来源轮转、SourceQuality、全文优先、每来源上限、近重复过滤和累计字符预算，为领域/模板 classifier 选择最多 18 个 chunk。classifier 确定模板后，`select_template_fact_evidence` 再从全部 GENERAL chunks 计算模板相关度并重排，不复用 classifier 子集；正向匹配优先于来源质量，质量和全文范围用于后续排序，同级候选轮转来源，按稳定 provenance 坐标打破并列。selector 使用模板 registry 的 `selection_terms`、对象、里程碑标签和关联 fact-type 描述；这些仅用于检索排序。正向候选不足 6 个时从 classifier evidence 按原序补足，并记录候选、选中、fallback、来源、字符与质量统计。两阶段的 bounded text view 不修改 Citation 或知识库原始 chunk。

Technology Fact Extractor 接收第二阶段选中的原始 GENERAL chunks：最多 30 个、每来源最多 3 个、每 chunk 3,200 字符、总字符预算 80,000；按 selector 顺序切为最多 3 个 chunk 的连续 batch，最多 2 个并发请求。模型 payload 使用 bounded view，fact 校验和派生 chunk 持久化使用同一批选中 chunk 的原始 Citation/provenance。响应按 batch 输入顺序合并，并验证 fact type registry、当前 batch source chunk、selected 集合及 domain/template tags，最后生成稳定 fact ID。批次异常按 fail-closed 处理：失败批次不接收事实；至少一批成功时形成 partial result 并记录信息缺口，全部失败则保留原始错误类别并终止。`FactExtractionReport` 持久化批次数、chunk 覆盖数、事实数、错误类别、拒绝引用/tag 数和未登记 fact type 分布。processor 版本为 `technology-semantic.v8`，模板 registry 为 `technology-templates.v2`；科技事实派生 KnowledgeChunk ID 绑定 source version 与稳定 fact ID，单次 upsert 批次的重复 chunk ID 在进入 repository 前由应用层拒绝。Runner 将 classifier 与 fact evidence 两份选择报告、批处理与错误类别分别写入 execution trace 和 review Markdown。

TechnologyFact 类型从版本化 `configs/knowledge/technology_fact_types.yaml` 读取。TechnologyFact 记录技术路线、技术成果、研发/验证/产品化/产业化里程碑；FinancialFact 记录财务、经营、商业、融资、客户订单金额、研发投入等经营维度。客户技术验证、试用、部署、验收和实际应用可作为 TechnologyFact，订单金额和收入仅由 Finance 处理。两个 extractor 可读取同一原始 GENERAL 来源，但各自在自己的结构化事实层建 ID 与 Citation。所有模板 evidence types、milestone fact type hints 与 inference rule fact type 条件必须在 Technology Fact Type Registry 登记。

Interpreter 返回后 processor trace 即转入 `persistence/derived_chunk_persistence`，记录 milestone 数量、状态分布和 blocked inference 数；派生 chunk 写入成功后进入 `semantic_profile_persistence`，Profile 保存完成后标记 `complete`。因此派生 chunk 写入失败与 profile 写入失败具有不同的最后子阶段。
### V2 第五阶段：科技金融联合推理

`backend/app/finance/` 提供金融事实抽取、规则 registry、证据选择、边界校验和处理编排。`TechnologyFinanceProcessor` 只读取企业当前 GENERAL + ENTERPRISE chunks，并要求先存在 `TechnologySemanticProfile`；输出持久化至 SQLite `technology_finance_profiles`，按 company、技术 profile、processor 和 finance registry 版本区分。运行入口为 `scripts/run_tech_finance_reasoning.py`。

事实层由单来源 `FinancialFact` 表达经营、研发、财务与融资披露；chunk ID 必须属于本轮当前输入，Citation 由代码复制原 chunk，不接受模型提供的新出处。`snippet_only` 金融事实可保留，但相关观察自动降为 `limited_support`。没有现金流、负债或订单资料只形成信息缺口，不转成负面事实。

`configs/finance/finance_registry.yaml` 版本化生命周期服务、创新积分制2.0可用信息维度、沪科积分贷业务场景、传统尽调字段及科技模板映射规则。政策信息是摘要与来源 metadata，不是政策原文证据。LLM 仅抽取 FinancialFact；mapper 确定性地按 registry 规则形成候选并绑定完整匹配 evidence bundle。带 `milestone_any` 的规则仅由指定 supported milestone 触发；通用规则按财务维度独立匹配。代码继续校验 rule、scenario、technology fact、financial fact、milestone 和 observation 类型。生命周期仅在明确证据规则加入后才可分类；当前 profile 默认 `unknown`，科技 milestone 单独记录为 `technology_stage`。Finance processor 版本为 `technology-finance.v4`。

联合结果包括融资活动、风险关注点、监测节点和金融信息缺口；每项 observation 带 TechnologyFact/FinancialFact ID、里程碑引用和 registry rule ID。输出 schema 不包含 approve、reject、credit_limit、信用评级或综合分字段，并以 `extra=forbid` 拒绝额外字段；系统不输出授信审批、额度或自动贷款决策。该阶段不调用旧 Evaluation Engine，也不接入旧 60/40 综合评分。

## 结构化模型 thinking 配置

`Settings.llm_enable_thinking` 对应可选环境变量 `KEHENG_LLM_ENABLE_THINKING`。未设置时，OpenAI-compatible structured request 不带该字段；显式 `true` 或 `false` 时，以布尔值写入请求体顶层。所有真实 structured model 脚本构造都传递此设置，不影响 timeout、模型选择或其它请求参数。

## V2 Evidence-First Report

`backend/app/report_v2/` 是独立的确定性报告组装层。`EvidenceFirstReportAssembler` 只读取 Company、最新 TechnologySemanticProfile、其匹配的 TechFinanceProfile、匹配的 EvidenceAssertionProfile 及 SQLite 中的 Source/Citation provenance；不调用模型、检索、评分或旧 report generator。profile 关联不一致、事实引用无法解析或 Source 缺失时拒绝组装。`GET /api/report/v2/company/{company_id}` 是只读入口，不触发上游 pipeline；旧 `POST /api/report/generate` 保持兼容。

报告以科技事实和金融维度的少量代表事实作为摘要，同时保留完整 fact ID 清单；citation 复制事实原始 Citation 与 Source，并展开 URL、chunk ID、摘录和 locator。技术 milestone 只消费已有 observations，按已选模板和 registry milestone 顺序展示，包括 no_evidence 与 blocked inferences。Finance evidence bundles 会展开技术/财务事实、里程碑引用和规则；状态不升级。金融缺口按维度归并，semantic gaps 去重并过滤运行诊断。报告不包含综合评分字段。End-to-end runner 在 Assertion 后保存 `evidence_first_report/report.json`，review.md 仅写摘要。


classifier 使用请求内临时 E1...En 引用而不向模型暴露稳定 KnowledgeChunk ID；返回引用经应用校验并映射为 profile 中的稳定 ID。无效引用的领域降级、逐模板筛除、去重及统计见 ClassifierReport。`semantic_evidence_selection` 作为兼容字段继续表示 classifier selection；profile 同时保存 `classifier_evidence_selection`、`fact_evidence_selection`、`classifier_processed_chunk_count` 和 `fact_processed_chunk_count`，旧 `processed_general_chunk_count` 表示两集合 chunk ID 的并集大小。语义 processor 当前版本为 `technology-semantic.v8`。

## V2 证据断言层

Finance 完成后，end-to-end review 调用 `EvidenceAssertionProcessor`。该层只读取最新 `TechnologySemanticProfile` 及其对应的 `TechFinanceProfile`，按确定性归一化组织已验证事实；不读取 GENERAL chunk、不调用模型/搜索、不创建向量，也不修改原始事实、里程碑或财务观察。断言结果单独持久化于 SQLite `evidence_assertion_profiles`，review 同时记录原子事实/断言数、压缩比、来源数分布和质量分布。异常会使 review 的 `evidence_assertions` stage 失败。

## Evidence Assertion v2 归一与聚类

`evidence-assertions.v2` 在 Assertion 层加载 repository 中已验证的 Company canonical name/aliases，仅对精确身份名和通用公司代词归一为 `__company__`；不做包含词或模糊实体推断。Finance period 仅将明确年/半年/季度表达规范化；无法识别时保留原始归一字符串，event_time 作为独立回退坐标。科技文本以 object 为主、predicate 为弱辅助，使用数字及型号 guard、确定性质量排序 anchor 与非传递聚类；Finance quantified 仍通过 dimension/主体/期间/规范金额签名归并。`grouping_method` 记录具体归组方式，profile/trace 记录合并、候选、拒绝和可疑 fuzzy cluster 计数。

文本相似度仅用于保守近重复归组，不构成语义推断或事实质量评级。模糊文本 assertion ID 以确定性代表表述构造；当新增更高质量代表表述时可能变化。不得将低压缩率解释成抽取失败；误合并的风险高于漏合并。
