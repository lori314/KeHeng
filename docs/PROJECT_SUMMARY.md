# KeHeng 项目总结

## 1. 项目背景

KeHeng（科衡）面向科技型企业资料分析和尽调辅助场景。企业技术路线、产品资料、公告和行业信息通常分散在多个 PDF 或网页中，人工阅读后不容易把结论、来源和评价依据放在同一条链路上。项目希望先把资料整理成可复核的证据，再输出技术与产业维度的辅助评价。

系统定位为信息整理和评价辅助工具，不替代金融机构、风控人员或业务人员的授信、投资和融资决策。

## 2. 技术路线

```text
PDF + 企业名称
  → 文档解析与切分
  → task_id 隔离的 RAG 知识库
  → E 编号证据检索
  → Technology Agent / Industry Agent 信息抽取
  → 确定性 Evaluation Engine
  → assessment_status 状态判断
  → Report Generator
  → React Web 展示
```

LLM 仅负责从检索证据中理解文字、提取指标和绑定 E 编号；Evaluation Engine 使用版本化指标、固定权重和确定性公式计算分数。证据不足时返回明确状态，不使用默认零分掩盖未知。

## 3. 主要贡献

### 3.1 E 编号证据链

文档切分后为证据片段保留文档名、页码、原文和 E 编号。编号在 Agent、Evaluation、Report 和 Web 页面之间传递，使用户可以从结论回到来源。

### 3.2 LLM 抽取与确定性评价分离

Technology Agent 和 Industry Agent 负责结构化信息抽取，评价模块负责按配置计算分数。这样可以分别测试模型理解和评分公式，也避免让 LLM 直接决定企业综合分数。

### 3.3 技术与产业双维评价

系统分别处理技术自主性、创新能力、知识产权、成熟度，以及市场潜力、行业成长性、竞争位置和政策环境，再按配置权重生成综合评价。

### 3.4 证据不足状态

系统支持 `fully_scored`、`partially_scored`、`insufficient_evidence` 和 `pipeline_failed`，明确区分可评分、部分可评分、资料不足和流程异常。

## 4. 实验结果

v1.1 使用 6 个固定合成案例，每个案例运行 5 次，共 30 次真实 LLM 运行。实验结果如下：

| 指标 | 结果 |
| --- | --- |
| First Success Rate | 100% |
| Final Success Rate | 100% |
| JSON Contract Success | 100% |
| Valid Evidence Rate | 100% |
| Technology 指标 MAE | 7.6471 |
| Industry 指标 MAE | 6.3333 |

合成案例由团队根据资料完整、关键材料缺失以及“计划量产”“尚未规模化”“正在研发”等语义问题人工设计，用于检查流程、证据和状态判断。六家公开企业案例用于观察真实资料的可运行性、证据链和报告展示，不设置融资预测金标准。

## 5. 当前限制

- 固定案例规模较小，尚不能代表大规模资料环境；
- 指标金标准主要用于回归检查，仍需要更多专家人工复核；
- 真实企业案例没有统一融资价值标签，系统分数不能解释为融资成功率或投资价值准确率；
- 当前主要支持含可提取文本的 PDF，扫描件、图表和复杂多模态材料支持有限；
- 当前任务状态保存在单个后端进程内，服务重启后不会自动恢复；
- 当前版本不包含用户权限、外部金融数据和正式生产数据平台。

## 6. 公开资料边界

公开仓库只保留合成示例、代码、配置模板、实验汇总和真实企业资料清单。API Key、运行时真实记录、私有配置以及企业原始 PDF 不应提交；真实资料目录通过 `manifest.json` 和下载说明保持来源可追踪。
