# KeHeng v1.0 路线规划

> 评审基线：v0.4  
> 评审目标：面向大学生金融科技竞赛，形成可演示、可解释、可验证的 v1.0 提交版本  
> 评审范围：项目文档、后端、前端、RAG、Agent、Evaluation、Report、Demo 脚本与现有测试

## 评审结论

KeHeng 当前已经形成“证据检索—指标提取—确定性评分—报告展示”的技术价值评估原型，核心架构方向正确，已经明显区别于仅做资料摘要的普通 RAG Demo。其最有竞争力的部分不是模型规模，而是“大模型/规则分析与确定性评价分工、评分可追溯、报告不重复计算”这一可信决策链路。

但当前版本仍更接近一个由脚本驱动的可解释技术评价样机，而不是可由评委现场操作的完整产品：Web 页面读取静态示例，后端尚未提供资料上传与完整分析接口；Technology Agent 仍是本地规则基线；RAG 使用轻量字符特征检索，尚无系统化效果评测；项目也只有单一虚构样例。v1.0 应优先补齐“动态端到端演示、效果验证、失败回退和陈述一致性”，而不是扩展更多 Agent、AHP 或复杂平台能力。

# 1. 当前项目状态评估

## 1.1 已完成模块

| 模块 | 当前状态 | 已具备能力 | 完成度判断 |
| --- | --- | --- | --- |
| 工程骨架 | 已完成 | 前后端分离、FastAPI 模块化目录、React + TypeScript + Vite、配置与测试目录 | 可作为后续开发基础 |
| PDF 文档处理 | 已完成基础版 | 基于页提取可复制文本，按滑动窗口切分，保留文档名、页码、原文和来源标识 | 适合文本型 PDF；不覆盖扫描件和复杂版面 |
| 本地 RAG | 已完成基础版 | 本地向量化、Chroma 持久化、按 `task_id` 隔离、证据检索 | 可离线运行；语义检索能力和效果指标不足 |
| Technology Agent | 已完成规则基线 | 抽取技术自主性、创新能力、知识产权、技术成熟度，输出结构化指标、优势、风险与 E 编号证据 | 逻辑可解释；尚不等同于真实大模型分析 |
| Evaluation Engine | 已完成 | 固定权重、确定性加权评分、缺失指标处理、分项解释、证据映射，保留 AHP 接口扩展点 | 是当前核心算法雏形 |
| Report Generator | 已完成 | 组合分析与评分结果，校验证据引用，生成结构化技术价值报告，不重新计算评分 | 职责边界清楚 |
| Web 展示 | 已完成静态版 | 展示综合分、维度分、指标详情、优势、风险和证据原文 | 适合截图；尚不能现场上传并动态分析 |
| Demo 脚本 | 已完成 | 从 PDF 依次产出 `technology_analysis.json`、`evaluation_result.json`、`technology_report.json` | 已形成命令行完整闭环 |
| 自动化测试 | 已完成关键基础测试 | 最近 v0.4 验证共 9 项测试通过，覆盖评分、权重、证据传递、缺失指标、PDF 链路、任务隔离、报告与 API | 缺少真实端到端 Web、检索质量和多样本测试 |

## 1.2 技术亮点

1. **大模型/分析模块不直接决定最终分数。** Technology Agent 负责理解材料、提取指标和绑定证据，Evaluation Engine 依据明确权重执行确定性评分，符合金融决策系统对职责分离的要求。
2. **证据链贯穿全流程。** 文档片段携带来源文档和页码，Agent 使用 E 编号引用证据，评分结果继续传递证据，报告生成阶段还会检查引用是否有效。
3. **报告不重复计算评分。** Report Generator 仅消费已有分析与评价结果，避免展示层和评价层产生口径漂移。
4. **具备事实约束意识。** 对“尚未规模化”“计划部署”等否定或未来语义进行保护，避免把规划性描述误判为已完成事实或高 TRL，可作为竞赛答辩中的具体可信 AI 案例。
5. **本地、轻量、可重复运行。** 当前 PDF 解析、检索、评分和报告链路不依赖外部 AI API，便于离线演示和故障回退。
6. **模块边界基本清晰。** RAG、Agent、Evaluation、Report 通过结构化模型衔接，适合 AI 辅助开发，也为后续替换模型或检索实现保留空间。

## 1.3 当前不足

### 产品闭环不足

- 前端读取内置静态 `technology_report.json`，企业名称也为示例内容；尚未调用后端完成动态分析。
- 后端只有健康检查和报告生成接口，没有资料上传、任务创建、全流程编排和进度/错误状态接口。
- Evaluation 与 Report 主要由 Demo 脚本串联，尚未收敛为统一的后端应用服务。
- 尚无用户从浏览器上传 PDF 后直接得到报告的真实演示路径。

### AI 与 RAG 能力不足

- Technology Agent 当前是关键词和规则驱动的离线基线，不能对外表述为“已经完成大语言模型分析”。
- 当前轻量字符特征向量适合离线原型，但语义泛化能力有限，近义表达、长句和跨段事实可能召回不足。
- 仅有一个虚构测试企业，尚无固定问题集、标准证据集或 Recall@K 等检索质量指标。
- 目前只处理可复制文本的 PDF。若继续以“多模态”作为已实现能力进行宣传，会与实际能力不一致。

### 评价可信度不足

- 评分过程是确定性的，但 Agent 的原始指标分仍来自规则，指标分档和边界需要更清楚的量表锚点。
- 权重配置有合理业务方向，但尚无专家访谈、文献依据或竞赛场景说明来支撑其可信度。
- 缺失指标采用可用权重归一化可以避免直接计零，但在材料覆盖率低时可能抬高总分；报告需要同时披露覆盖率或触发“不足以评分”。
- 固定权重提供器与抽象接口的校验职责存在不一致，配置集合标识和计算方法的校验需要在后续迭代中收敛。

### 工程与展示不足

- 根目录 `rag/`、`agents/` 与 `backend/app/` 下的实际实现并存，容易让新开发者误判代码唯一来源。
- 配置文件、包注释和后端版本号存在 v0.1、v0.2、v0.4 并存的版本漂移。
- 尚无前端测试、浏览器端回归测试、损坏文件/空文本 PDF/超大文件等异常路径验证。
- 当前评审环境尚未形成可识别的 Git 提交基线；v1.0 前应建立清晰的版本提交、发布标签和可复现实验记录。
- 没有一键启动、环境预检、离线备用报告和现场演示故障预案。

## 1.4 与比赛展示要求的匹配程度

| 展示维度 | 匹配度 | 评审意见 |
| --- | --- | --- |
| 选题价值与金融科技相关性 | 高 | 科技企业技术价值难评估、材料非结构化、金融机构需要依据和风险提示，问题真实且叙事完整 |
| 架构创新性 | 较高 | “AI 提取事实 + 确定性评价 + 证据报告”比单纯问答或摘要更有辨识度 |
| 可解释性 | 高 | 已具备 E 编号、来源页码、原文、评分解释和引用校验 |
| 现场可操作性 | 中低 | 目前 Web 为静态展示，真实闭环需要命令行脚本，不适合评委直接操作 |
| AI 能力真实性 | 中低 | 当前规则基线有工程价值，但尚未完成可配置的大模型结构化提取路径 |
| 多模态能力 | 低 | 当前仅支持文本型 PDF，不应把规划能力描述为已完成能力 |
| 评价可信度 | 中 | 计算透明，但指标分档、权重依据和样本验证仍不足 |
| Demo 稳定性 | 中 | 核心逻辑可离线运行，但缺乏一键启动、异常处理和连续演练记录 |
| 视觉呈现 | 中高 | 信息结构清晰、适合截图，仍需动态状态、覆盖率和证据交互增强 |

总体判断：当前项目已经具备进入竞赛作品打磨阶段的“内核”，但尚未达到 v1.0 提交条件。若下一阶段优先完成动态 Web 闭环与可信性验证，而不是扩张功能范围，项目有机会形成一个主题集中、逻辑自洽、可现场证明的高质量作品。

# 2. 当前架构评审

## 2.1 总体架构

当前采用 React 前端、FastAPI 模块化单体后端、本地 RAG、专业 Agent 接口、独立 Evaluation Engine 和纯报告生成器，适合单人或小型学生团队的短周期开发。此阶段继续维持模块化单体优于拆分微服务：部署简单、调试链短、失败点少，同时已有接口足以支持未来替换局部实现。

推荐的 v1.0 目标调用链为：

```text
用户上传 PDF
    ↓
Web 页面创建分析任务
    ↓
FastAPI 统一应用服务
    ↓
PDF 解析与任务级知识库
    ↓
检索 + Technology Agent 指标提取
    ↓
Evaluation Engine 确定性评分
    ↓
Report Generator 组装并校验证据
    ↓
Web 动态展示报告与证据
```

## 2.2 后端架构

### 应该保持

- 保持 FastAPI 模块化单体，不在比赛版本中拆微服务。
- 保持 Pydantic 结构化输入输出与边界校验。
- 保持 API、核心配置、RAG、Agent、Evaluation、Report 分层。
- 保持 `/health` 与清晰的 HTTP 错误响应风格。

### 需要调整

- 增加统一应用编排层，将解析、入库、分析、评价和报告从 Demo 脚本收敛为一个可复用业务用例，避免 API 与脚本各自拼装流程。
- 提供面向 Demo 的资料分析接口，接收 PDF 并返回任务报告；在计算耗时可控时优先采用简单同步流程，不为比赛提前引入消息队列。
- 增加文件类型、大小、空文本、损坏 PDF、任务清理和超时边界。
- 统一版本号、配置版本和运行模式，并让报告记录实际使用的配置版本。
- 明确 `backend/app/` 是运行时代码唯一来源，清理或说明根目录占位目录的用途。

## 2.3 RAG 设计

### 应该保持

- 保持每个 chunk 的文档名、页码、原文和稳定来源标识。
- 保持 `task_id` 在检索前进行强制过滤，避免不同企业资料串库。
- 保持本地可运行模式，作为比赛现场的可靠回退方案。
- 保持向量化、存储和检索的接口抽象，允许替换实现。

### 需要调整

- 将当前字符特征检索明确标记为离线基线，增加轻量中文语义向量或关键词 + 向量的混合检索方案。
- 建立小型标准证据集，使用 Recall@K、有效证据命中率和跨任务泄漏率评价检索，而不是只凭单次输出判断效果。
- 对空文本 PDF、扫描件、表格和跨页内容给出明确策略。若 v1.0 继续宣称具备多模态能力，至少实现一条受控的扫描 PDF/OCR 证据路径；否则应将范围表述为“文本型 PDF，架构可扩展至多模态”。
- 对检索结果设置最小相关性或“无充分证据”状态，避免低相关片段被强行用于评分。

## 2.4 Agent 设计

### 应该保持

- 保持 Agent 只负责材料理解、事实提取和指标建议，不输出最终综合分。
- 保持固定 JSON 契约、E 编号和来源信息。
- 保持否定语义、未来计划和未验证状态保护。
- 保持规则分析作为离线回退和回归测试基线。

### 需要调整

- 将“规则基线”和“模型提取模式”命名区分清楚，避免将当前规则误称为 LLM Agent。
- 在不改变输出契约的前提下增加模型适配层，使真实模型调用可配置、可关闭、失败时可降级；比赛版本只需一个稳定模型路径，无需同时接入多个框架。
- 对每个指标增加提取状态，例如“有充分证据、证据不足、存在冲突、未提及”，让下游能够区分低分与缺失。
- 强化证据白名单：Agent 只能引用本次检索结果中的 E 编号，报告生成阶段继续进行引用完整性校验。
- v1.0 前不应同时开发 Industry Agent 和 Finance Agent。第二类 Agent 仅作为 v0.6 之后的条件增强项，优先考虑与金融场景更相关的 Risk Agent。

## 2.5 Evaluation 设计

### 应该保持

- 保持确定性评分、固定权重和透明公式。
- 保持评分配置外置、证据映射、分项解释和缺失指标不崩溃。
- 保持 AHP 的接口扩展空间，但不在 v1.0 主链路中实现 AHP。
- 保持报告层不能修改或重新计算评分的约束。

### 需要调整

- 为 0—100 分建立可答辩的分档锚点，说明什么证据对应 20、40、60、80 分，降低指标提取的主观性。
- 为当前权重补充融资场景解释、专家评阅记录或参考依据。权重合理性说明比形式化套用 AHP 更优先。
- 修复并统一权重配置的集合标识、方法和合计校验职责，确保所有权重提供器遵循相同契约。
- 在输出中披露材料覆盖率、有效权重合计和缺失指标；覆盖率低于阈值时应输出“材料不足，暂不形成综合结论”，而非仅归一化后给出看似完整的高分。
- 在固定样例上做简单敏感性说明，证明小幅调整权重不会导致结论完全反转；不需要开发复杂敏感性分析平台。

## 2.6 Report 设计

### 应该保持

- 保持 Report Generator 为确定性纯组装器，不调用模型、不重新评分。
- 保持优势、风险、指标和引用之间的证据完整性检查。
- 保持结构化 JSON 为前后端之间的主契约。

### 需要调整

- 增加企业名称、任务标识、生成时间、文档范围、模型/规则版本、指标配置版本和覆盖率等报告元数据。
- 减少同一证据在多层对象中的无约束重复，建立统一 `references` 索引，其余位置主要保存 E 编号，避免前端展示口径不一致。
- 将现有 Markdown 模板真正用于可读报告导出，至少支持 Markdown 下载；PDF 导出可作为可选增强，不应阻塞主流程。
- 明确“技术价值评分是辅助评价，不构成授信或投资决策”的使用边界。

## 2.7 前端展示

### 应该保持

- 保持当前以信息层级和证据可读性为主的简洁页面，不为比赛投入复杂动效。
- 保持综合分、维度分、优势、风险和原文证据的同屏关联。
- 保持响应式基础布局和 TypeScript 数据模型。

### 需要调整

- 从静态 JSON 改为调用后端完整分析接口，移除动态路径中的硬编码企业名称。
- 增加文件选择、分析中、成功、失败、重新分析和加载内置样例状态。
- 增加材料覆盖率、配置版本和“证据不足”提示，避免单独展示一个缺少语境的总分。
- 证据卡片可按 E 编号跳转或展开来源页码和原文；不需要先做复杂图表。
- 保留“内置样例一键展示”作为现场断网或模型不可用时的备用入口，但必须清楚标注为示例结果。

# 3. v1.0 目标定义

## 3.1 v1.0 产品定位

v1.0 应被定义为：面向竞赛展示的科技企业技术资料智能分析与可解释价值评价系统。它能够在受控样例范围内，由用户从 Web 上传企业技术 PDF，自动得到带证据的技术指标、确定性评分、风险提示和标准化报告，并在模型或网络异常时提供可解释的回退路径。

v1.0 不是生产级银行尽调平台，不宣称替代专家，也不要求覆盖企业经营、财务、产业链和合规的全部尽调维度。

## 3.2 必须完成（Must Have）

1. **浏览器端真实闭环。** 用户上传受支持 PDF 后，无需手工运行脚本即可得到动态技术价值报告。
2. **企业资料隔离与基础安全。** 每次分析具有独立 `task_id`，校验文件类型和大小，异常文件不会导致服务崩溃或资料串库。
3. **多维技术评价。** 至少稳定覆盖技术自主性、创新能力、知识产权能力和技术成熟度，并汇总为创新、知识产权、成熟度等展示维度。
4. **完整证据链。** 每个关键结论和参与评分的指标都能追溯到 E 编号、来源文档、页码和原文片段；无证据时明确标记，不强行形成结论。
5. **确定性评分。** 最终分数只由 Evaluation Engine 依据版本化指标、权重和公式计算，模型与报告生成器均不能重新决定分数。
6. **自动报告与 Web 展示。** 动态显示综合分、分项分、覆盖率、优势、风险、评分依据和引用，并支持保存结构化结果或 Markdown 报告。
7. **可信 AI 路径。** 至少提供一个可配置的结构化信息提取实现，并保留当前规则基线作为离线回退；若比赛现场不启用真实模型，必须如实说明。
8. **可验证效果。** 建立 3—5 个固定公开或合成样例、标准证据和关键回归用例，展示检索命中、引用完整性、任务隔离和否定语义保护结果。
9. **稳定演示与发布基线。** 一键启动或明确的短命令启动、环境预检、内置样例、失败提示、离线备用报告、完整测试和前端构建均通过，并形成可追踪的 v1.0 发布标签。
10. **能力陈述一致。** 若保留“多模态”作为 v1.0 已实现卖点，必须支持至少一种扫描 PDF/OCR 场景并保留证据位置；否则在文档和答辩中明确其为后续扩展能力。

## 3.3 可选增强（Nice To Have）

- Risk Agent：在技术材料范围内补充证据约束的技术实施、替代、知识产权和商业化风险，不直接改变 Evaluation 分数。
- 多 PDF 合并分析与文档级筛选。
- 企业技术指标对比，但必须保证同一指标版本、相同资料口径和清晰免责声明。
- 雷达图、指标条形图和证据分布等轻量可视化。
- Markdown/PDF 报告导出和打印样式。
- PDF 页内证据高亮或原文定位。
- 在主闭环稳定后增加有限的 OCR 版面处理能力。

## 3.4 不建议实现

- 复杂用户权限、组织体系、收费和审批流。
- 大规模外部数据库、数据湖、实时爬虫或企业数据平台。
- 微服务、消息队列、Kubernetes 和高并发分布式架构。
- 自研或训练大语言模型、自研向量数据库。
- 为展示算法复杂度而提前实现 AHP、知识图谱或多套 MCDA 方法。
- 同时铺开 Industry Agent、Finance Agent、法务 Agent 等多个不完整模块。
- 在缺少真实标注和专家依据时宣称评分具有授信、投资决策或行业普适效力。
- 依赖现场网络和单一外部模型才能完成的演示方案。

# 5. 推荐下一阶段开发路线

## 5.1 v0.5：从静态样机到可操作闭环

### 目标

让评委能够在浏览器中上传一份受支持的企业技术 PDF，并直接看到由当前 RAG、Technology Agent、Evaluation Engine 和 Report Generator 生成的动态报告。

### 实现内容

- 建立统一的技术尽调应用服务，按固定顺序编排解析、入库、检索、指标提取、评分和报告。
- 增加面向 Demo 的资料分析接口，支持 PDF、企业名称和任务标识；当前数据规模下优先同步或简单轮询，不引入消息队列。
- 增加扩展名/MIME、大小、空文本、损坏文件、临时文件清理和错误响应。
- 前端增加上传、分析中、成功、失败、重新分析和内置样例入口，动态渲染后端报告。
- 在报告中补充企业、任务、资料范围、生成时间、规则/模型版本、指标配置版本和材料覆盖率。
- 统一版本号、配置说明和运行时代码来源；修复权重配置校验职责不一致；建立干净的 Git 提交基线。
- 增加完整分析 API 测试和最小浏览器回归路径。

### 完成标准

- 在全新启动的本地环境中，从浏览器选择示例 PDF 到显示报告，不需要手工执行 Demo 脚本或复制 JSON。
- 同时或连续分析两个任务时，检索证据不存在跨 `task_id` 泄漏。
- 损坏 PDF、空文本 PDF 和不支持格式均显示明确错误，服务保持可用。
- 动态页面不再硬编码示例企业；内置样例被清楚标注为备用演示数据。
- 后端测试、完整链路测试和前端构建全部通过，启动说明可由非开发成员复现。

## 5.2 v0.6：可信 AI 与评价验证

### 目标

证明系统不仅“能生成报告”，而且在受控样例上能够稳定检索正确证据、约束模型输出，并解释指标分和权重。

### 实现内容

- 在保持 Technology Agent 输出契约不变的前提下，增加单一、可配置的结构化模型提取路径，并保留规则离线回退。
- 记录模型、提示词、规则和指标配置版本；模型失败、超时或未配置时给出可见降级状态。
- 引入轻量中文语义向量或混合检索，并继续在检索前强制执行 `task_id` 过滤。
- 建立 3—5 个固定公开或合成样例，覆盖明确优势、证据不足、否定语义、未来规划和相互冲突描述。
- 为样例建立关键问题、期望证据和预期指标区间，统计 Recall@K、引用完整率、跨任务泄漏率与否定语义回归结果。
- 细化指标评分锚点，邀请指导教师或具有科技金融经验的人员审阅权重理由，并保留评阅记录。
- 增加材料覆盖率阈值与“不足以形成综合评分”的路径；进行小范围权重变化说明，但不实现 AHP。
- 若比赛定位坚持“多模态已实现”，完成最小扫描 PDF/OCR 样例；否则统一收窄产品表述。

### 完成标准

- 在固定测试集上，关键证据 Recall@5 建议达到 80% 以上；若样本量较小，必须同时披露样本规模，不能把该数字表述为通用效果。
- 所有报告关键结论均引用本任务检索得到的有效 E 编号，结构化引用完整率为 100%。
- 跨任务证据泄漏率为 0；既有否定语义和未来计划回归用例全部通过。
- 每个参与评分的指标均有有效证据、分档解释和配置版本；材料覆盖不足时不输出误导性的完整总分。
- 无网络或模型不可用时，规则回退仍能完成内置样例演示，并在页面明确显示运行模式。
- 权重与评分量表具有书面业务理由和至少一次外部审阅记录。

## 5.3 v1.0：竞赛提交冻结与稳定交付

### 目标

冻结一个范围真实、现场稳定、证据完整、演示流畅、可回答质疑的竞赛提交版本。

### 实现内容

- 冻结指标体系、权重、模型/规则版本、提示词、测试样例和报告契约，非阻断性功能不再进入主分支。
- 优化但不重做 Web 信息架构：突出上传、评分、覆盖率、优势、风险、评价过程和证据跳转。
- 提供一键启动或极简启动脚本、环境预检、依赖锁定、本地资源准备、数据清理和重置说明。
- 准备内置样例、静态备用报告、演示录屏和网络故障预案。
- 完成测试汇总、已知限制、隐私说明、免责声明、部署说明和 v1.0 发布标签。
- 制作 3—5 分钟演示脚本与答辩材料，演示“原文证据—指标提取—确定性评分—报告结论”的完整因果链。
- 仅当 v0.6 所有质量门槛已满足且不影响稳定性时，选择性加入 Risk Agent 或轻量图表；否则留入后续路线。

### 完成标准

- 按 README 在一台干净测试环境完成启动和样例分析，非核心开发者可以照步骤复现。
- 标准 Demo 连续运行 10 次无阻断性失败，且网络中断时可切换到明确标注的离线回退。
- 至少 3 个代表性样例可以从 Web 上传并生成字段完整、引用有效的报告。
- 动态路径无硬编码企业信息，报告展示的分数与 Evaluation Engine 输出完全一致。
- 后端测试、端到端测试、关键回归测试和前端生产构建全部通过。
- 能用一页材料说清权重理由、量表锚点、样本规模、评测结果和适用边界。
- 形成干净的 v1.0 提交、发布标签和可恢复的现场演示包。

# 6. 比赛展示建议

## 6.1 评委最值得看到的内容

建议用一条真实、短而完整的故事线演示：

1. **先讲痛点。** 科技企业的核心价值藏在技术白皮书、专利和验证材料中，金融人员阅读成本高，传统评分难以说明“结论来自哪里”。
2. **现场上传资料。** 使用一份内容经过授权、公开或完全合成的文本型 PDF，并明确资料范围。
3. **展示证据检索。** 让评委看到系统不是直接总结全文，而是找到带文档名和页码的关键片段。
4. **展示 AI 的正确角色。** 强调 AI/规则分析负责把非结构化材料转为结构化指标和 E 编号，不负责拍板最终分数。
5. **展示确定性计算。** 打开指标得分、权重和加权过程，说明相同输入和相同配置会得到相同分数。
6. **展示一个事实约束案例。** 重点演示“尚未规模化”不会被识别为已完成规模部署或 TRL 8，体现否定语义与证据校验。
7. **展示报告结论。** 从优势或风险点击回原文证据，证明结论、评分和来源形成闭环。
8. **最后说明边界。** 系统是尽调辅助和价值评估工具，不替代专家、授信审批或投资决策。

推荐答辩主张：

> KeHeng 的创新不在于让大模型直接给企业打分，而在于让 AI 负责理解复杂材料，让确定性评价模型负责执行透明规则，并让每个结论都能返回原始证据。

## 6.2 权重问题的推荐回答

不必用 AHP 包装当前权重。应说明当前权重是面向早期科技企业融资场景的版本化原型配置：创新能力与技术自主性更直接反映差异化竞争优势，技术成熟度反映落地可行性，知识产权主要反映保护与壁垒能力。随后主动披露其尚需更多专家和样本校准，并展示评阅记录、配置版本以及小范围权重变化下结论是否稳定。

## 6.3 应避免强调的内容

- 不要把当前规则基线描述为已经完成大语言模型推理。
- 未完成 OCR/图像理解前，不要演示扫描件，也不要把“多模态”描述成已落地能力。
- 不要把 72.75 等示例分数描述为企业的绝对真实价值或融资结论。
- 不要宣称系统已覆盖完整的产业、财务、法律与合规尽调。
- 不要把 AHP、Industry Agent、Finance Agent 等接口或规划表述为已实现功能。
- 不要花大量时间介绍框架名称、目录结构或前端动效；评委更关心证据、规则、有效性与实际价值。
- 不要只播放录屏。优先现场操作，同时准备录屏和静态报告作为故障备用。
- 不要隐瞒材料不足和模型回退。透明显示运行模式、覆盖率和已知限制会增强可信度。

# 7. 技术风险分析

| 风险 | 当前表现 | 可能影响 | 解决方案 | 验收信号 |
| --- | --- | --- | --- | --- |
| RAG 效果风险 | 字符特征检索语义能力有限，只有单一样例，无标准召回评测 | 关键事实漏检，错误证据进入 Agent，报告看似完整但依据不充分 | 增加轻量语义或混合检索；建立问题—标准证据集；设置相关性阈值和“无充分证据”；保留 `task_id` 前置过滤 | 固定集 Recall@5 达到预设目标；跨任务泄漏为 0；低相关时能够拒绝形成结论 |
| 大模型幻觉风险 | 当前规则基线风险较低，但接入模型后可能补写资料中不存在的事实、误读否定语义或引用不存在的证据 | 损害尽调可信度，导致指标和风险结论失真 | 使用严格结构化输出；限制只能引用检索候选 E 编号；继续做引用完整性校验；版本化提示词；低随机性；增加否定、未来计划、冲突和提示注入测试；保留规则回退与人工复核提示 | 关键结论引用完整率 100%；无效 E 编号被拒绝；否定语义回归全部通过；模型故障可降级 |
| 评分可信度风险 | 计算确定，但原始指标分档、权重和缺失归一化尚未充分验证 | 评委质疑“为什么是这个分数”，低覆盖资料可能产生过高分 | 建立可观察的评分锚点；记录权重业务理由和专家评阅；披露覆盖率与有效权重；低覆盖时不出总分；展示公式和配置版本；做简单权重扰动说明；统一权重校验实现 | 每个分数可追溯到指标、量表和证据；权重合计与版本校验通过；低覆盖样例不产生误导性总分 |
| Demo 稳定性风险 | Web 为静态样例，真实闭环依赖脚本；依赖、端口、Chroma 状态、模型网络都可能造成现场失败 | 无法在有限时间内完成演示，影响整体评分 | 收敛统一分析 API；提供一键启动、预检和数据重置；锁定依赖与本地资源；准备内置样例、静态报告和录屏；设计清晰加载/失败状态；提前连续演练 | 标准流程连续 10 次成功；干净环境可复现；断网可回退；异常文件不会使服务退出 |
| 多模态宣传风险 | 当前只支持可复制文本的 PDF | 能力陈述与现场实际不符，容易被追问击穿 | 二选一：实现受控扫描 PDF/OCR 最小链路，或把 v1.0 范围明确为文本型 PDF 并将多模态列为后续扩展 | 文档、PPT、页面和实际支持格式一致 |
| 数据安全与隐私风险 | 本地原型缺少完整权限与生命周期管理 | 演示若使用真实企业材料可能泄露敏感信息 | 比赛只使用公开、授权或合成材料；默认本地处理；不在日志记录全文；任务结束可清理临时文件和向量数据；页面显示资料使用说明 | 演示包不含未授权材料；任务数据可清理；日志无企业全文和密钥 |
| 工程一致性风险 | 多处版本标识、占位目录和运行代码来源不一致，尚无清晰发布基线 | 开发误改、提交遗漏、现场环境与演示结果不一致 | 明确唯一运行代码目录；统一版本和配置；建立变更清单、自动测试、Git 提交与 v1.0 标签；冻结提交后只接受阻断性修复 | 发布提交可追踪；README 与运行行为一致；提交包无未说明的本地修改 |

## 风险处理原则

1. 先保证在明确支持范围内稳定成功，再扩展文档类型、模型和 Agent 数量。
2. 对“证据不足、材料未提及、模型不可用、文件不受支持”给出显式状态，不用猜测填补空白。
3. 所有关键配置和结果都应版本化，使竞赛报告、现场输出和测试结果能够对应到同一基线。
4. 对效果数字同时披露样本规模、测试范围和限制，避免把小样本结果外推为生产性能。

下一项开发任务应确定为 **v0.5：Web 上传驱动的端到端技术评估闭环**。其交付重点是统一后端编排、动态分析接口、前端上传与状态管理、报告元数据、异常处理和离线样例回退。完成这一阶段后，再进入 v0.6 的模型提取、混合检索和可信性评测；在这些质量门槛通过前，不启动新 Agent、AHP 或复杂平台建设。
