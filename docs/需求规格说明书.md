# 科衡需求规格说明书

## 1. 文档目的

本文描述科衡首期建设的业务目标、用户角色、功能与非功能需求、约束和验收方向，作为产品、设计、研发、测试与验收的共同基线。当前内容为基于项目背景形成的初稿，尚需通过用户访谈、样本分析与合规评审细化。

## 2. 产品定位与使用边界

科衡是一套面向科技型企业融资场景的辅助尽调与价值评估系统。它整合获授权的企业资料和知识来源，辅助金融机构分析企业的技术价值、产业潜力、财务经营质量与风险，并形成可解释报告。

系统不代替正式审计、法律意见、资产评估或金融机构的最终决策；不得在缺乏授权或充分证据时生成确定性事实；高影响结论必须由人复核后使用。

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 尽调任务 | 围绕一个目标企业、明确资料范围和分析目的创建的工作单元 |
| 证据 | 能定位到来源、位置、时间和访问权限的原始资料片段或数据记录 |
| 专项分析 | 技术、产业、财务、风险等主题的结构化分析结果 |
| 待核验项 | 因缺失、冲突、过期或可信度不足而需要人工补充确认的信息 |
| 评价版本 | 指标、权重、阈值和规则的一个不可变版本 |

## 4. 用户角色

| 角色 | 主要诉求 | 主要权限方向 |
| --- | --- | --- |
| 尽调分析人员 | 创建任务、上传资料、查看证据与修订报告 | 管理获授权任务和报告草稿 |
| 技术/行业/财务专家 | 复核专项结论和依据 | 查看相关材料、批注与确认 |
| 风控/审批人员 | 查看综合评价、风险和信息缺口 | 只读或审批，保留意见 |
| 系统管理员 | 用户、权限、配置和运行维护 | 不默认获得业务资料内容权限 |
| 审计/合规人员 | 追查数据访问和结论生成过程 | 查询审计记录，不修改业务结论 |

角色与权限矩阵需在部署机构的制度基础上确认。

## 5. 典型业务流程

1. 用户创建尽调任务，登记目标企业、场景、资料授权和报告要求。
2. 用户上传或接入资料，系统进行格式、安全、完整性和可解析性检查。
3. 系统解析资料、提取元数据并建立受权限控制的检索索引。
4. 专业智能体基于授权证据形成专项分析，标注引用、置信度和待核验项。
5. 评价模块依据已生效的指标和权重生成结构化结果及解释。
6. 报告模块汇总事实、分析、风险、冲突和信息缺口。
7. 专家或尽调人员核验、批注、修订并提交审批。
8. 系统冻结发布版本，记录数据、模型、规则、配置和人工操作链路。

## 6. 功能需求

### 6.1 任务与资料管理

- **FR-001** 系统应支持创建、查询、更新和归档尽调任务，并记录企业、场景、负责人、状态和时间。
- **FR-002** 系统应记录资料使用授权、来源、上传者、获取时间、有效期和密级。
- **FR-003** 系统应支持配置允许的资料类型，并对恶意文件、损坏文件、重复文件和超限文件给出明确处理结果。
- **FR-004** 系统应展示资料处理状态、失败原因和可重试动作，不得静默丢失资料。
- **FR-005** 用户应能标记资料版本、失效资料和优先证据，历史记录不可被无痕覆盖。

### 6.2 文档解析与知识检索

- **FR-101** 系统应从支持的资料中提取内容、结构和页码/位置等定位信息，并保留与原件的关联。
- **FR-102** 系统应按任务和权限隔离知识内容，禁止跨企业或跨任务越权检索。
- **FR-103** 检索结果应包含来源、定位、时间、相关度及必要的可信度元数据。
- **FR-104** 用户应能从分析结论跳转或回溯到对应证据，无法定位的内容不得标记为已证实事实。
- **FR-105** 系统应识别缺失、冲突、重复和可能过期的证据，并向后续分析暴露该状态。

### 6.3 专项智能分析

- **FR-201** 技术分析应覆盖技术创新性、成熟度、知识产权、研发与工程化能力等已配置主题。
- **FR-202** 产业分析应覆盖市场需求、竞争格局、产业链位置、政策与商业化等已配置主题。
- **FR-203** 财务分析应覆盖成长、盈利、现金流、负债、融资和异常勾稽等已配置主题。
- **FR-204** 每项分析输出应包含结论、证据引用、推理说明、不确定性和待核验事项。
- **FR-205** 证据不足或冲突时，系统应降级、拒绝确定性判断或请求人工复核，不得虚构补全。
- **FR-206** 专项分析失败、超时或被人工否决时，应保留状态并允许安全重试或转人工处理。

### 6.4 指标评价

- **FR-301** 系统应支持版本化管理指标、尺度、权重、阈值、适用范围和审批状态。
- **FR-302** 每个得分应可追溯到指标版本、输入证据、计算/判断理由和责任主体。
- **FR-303** 系统应定义缺失值、异常值、冲突证据和否决性风险的处理规则。
- **FR-304** 系统应支持权重敏感性或情景对比，避免只展示单一总分。
- **FR-305** 未经审批的指标配置不得用于正式报告。

### 6.5 报告与协作审阅

- **FR-401** 系统应按版本化模板生成报告草稿，至少包括摘要、企业与资料范围、专项分析、评价、风险、信息缺口和证据索引。
- **FR-402** 报告应区分事实、模型推断、规则结果和人工意见，并展示生成时间与适用范围。
- **FR-403** 用户应能批注、修订、接受或驳回 AI 结论，AI 不得覆盖人工意见。
- **FR-404** 系统应保存报告版本及差异，发布版本须经过配置的复核或审批流程。
- **FR-405** 报告导出格式和水印策略待业务确认；导出操作应受权限控制并被审计。

v0.4 已实现 FR-401 的最小技术报告草稿：系统从既有 Technology Agent 与 Evaluation Engine 结果生成结构化 JSON，并在 Web 页面展示评分、优势、风险和证据索引。v0.5 进一步实现文本型 PDF 上传、进程内任务状态、任务独立知识库、统一分析服务和动态 Web 报告。当前不包含任务持久化、报告版本、批注、审批和导出，不能视为 FR-001 或 FR-402 至 FR-405 的完整实现。

Iteration 03 已在该最小闭环提供显式“规则演示/真实模型”选项；规则演示只分析技术，真实模式要求后端模型配置并尝试技术与产业两个模块。任务应区分模块故障与业务证据不足、保留部分成功、展示逐指标覆盖分母和引用位置；补材料建议基于未评分指标的透明规则映射。真实模式无配置不得静默回退。该实现仍是本地单进程原型，不实现任务持久化、机构级权限或正式审批。

### 6.6 权限、配置与审计

- **FR-501** 系统应实施基于组织、角色、任务和资料密级的访问控制。
- **FR-502** 对查看、上传、下载、检索、分析、配置、审批和导出等关键操作应记录审计日志。
- **FR-503** 模型、提示词、知识库、指标、权重和报告模板应记录版本及生效范围。
- **FR-504** 系统应支持撤销资料授权后的访问阻断及按制度执行的删除/保留流程。
- **FR-505** 管理员权限和业务数据访问权限应分离，敏感操作支持复核或双人控制。

## 7. 非功能需求

- **NFR-001 安全与隐私：** 传输和存储采用适当保护；密钥集中管理；日志与测试数据脱敏；防止提示词注入、越权检索和敏感信息外泄。
- **NFR-002 可解释性：** 关键结论和评分可回溯至证据、规则、模型与人工操作；引用定位可被用户核验。
- **NFR-003 可靠性：** 长任务支持状态持久化、幂等重试和失败恢复；部分模块失败不应伪装为完整成功。
- **NFR-004 性能：** 文档规模、并发、交互响应和报告时限需通过样本基线确定；系统应监控耗时、排队和资源消耗。
- **NFR-005 可维护性：** 模块接口明确，配置外置，具备自动化测试、结构化日志和环境一致性说明。
- **NFR-006 可移植性：** 模型、向量库和文档解析组件通过适配层隔离，部署形态在选型阶段确定。
- **NFR-007 可用性：** 用户能够理解任务状态、错误原因、证据关联和需人工处理的动作。
- **NFR-008 可审计性：** 正式报告的生成条件可还原，审计记录防篡改且保留周期可配置。

量化阈值将在获得真实样本和机构级服务目标后补充，不以无依据数值作为验收承诺。

## 8. 数据与合规约束

- 仅处理拥有合法授权且与尽调目的相关的数据。
- 生产敏感数据不得进入源代码仓库、普通日志或未批准的模型服务。
- 外部数据必须记录来源、许可、获取时间和使用限制。
- 涉及个人信息、商业秘密和重要数据的处理，应按适用制度完成评估与审批。
- 输出需包含使用限制，避免将推断性信息误表述为已核实事实。

## 9. 初步验收场景

1. 使用一组获批准的脱敏资料创建任务并完成处理，用户可查看失败和缺失资料。
2. 对报告中的抽样结论能够回溯到正确原文位置，并能发现无依据或错误引用。
3. 证据相互冲突时，系统展示冲突且要求复核，而非静默选取其一。
4. 切换评价版本后能够说明分数变化来源，并保留旧版本报告。
5. 无权用户无法查看、检索、导出其他任务资料，越权尝试进入审计记录。
6. 模型服务不可用时任务可恢复或转人工，不产生伪造的完整报告。

## 10. 待确认需求

- 首期支持的文档格式、单任务资料规模和并发量。
- 是否以及如何接入工商、专利、司法、行业和市场等外部数据。
- 正式报告模板、审批流程、电子签章与导出格式。
- 行业分类、企业阶段、融资产品与指标体系的映射。
- 部署方式、身份源、保留期限、灾备目标和服务等级。

## v1.1 结构化输出要求

正式 LLM 模式必须显式报告结构化契约失败，不得自动切换 rule。Provider 可启用 JSON mode，并允许最多一次仅格式修复；修复不得改变事实、证据或评分。系统需记录首轮有效、修复触发、修复成功和最终状态，便于版本冻结与人工复核。
