# KeHeng v1.0 LLM 失败分析

## 1. 数据范围

本分析来自 `runtime/experiments/v10/raw_runs.json` 和 `error_breakdown.json`。6 个固定案例各运行 5 次，共 30 次 LLM 流程；综合案例每次包含 Technology 与 Industry 两次模型调用。失败分类只统计真正影响流程的失败；未来语义风险等质量问题另列在 `error_cases.json`，不与 API 失败混为一谈。

## 2. 分类结果

| 类别 | 次数 | 失败运行占比 | 是否可恢复 | 建议 |
|---|---:|---:|---|---|
| schema_failure | 8 | 100% | 通常不可恢复 | 优化提示词、结构化输出和字段契约；不自动补字段 |
| HTTP timeout | 0 | 0% | 是 | 有限指数退避，并记录最终错误 |
| 429 / 限流 | 0 | 0% | 是 | 降低并发、退避、重试 |
| 5xx | 0 | 0% | 是 | 有限重试并保留首次/最终状态 |
| 网络连接错误 | 0 | 0% | 是 | 网络与连接池诊断 |
| 空内容 | 0 | 0% | 否 | 明确失败并进入人工复核 |
| Markdown code fence | 0 | 0% | 可解析时 | 仅剥离合法 code fence，不从自然语言猜字段 |
| JSON 语法错误 | 0 | 0% | 否 | 记录原始响应并修正提示词 |
| evidence 字段不合法 | 0 | 0% | 否 | 拒绝结果，禁止伪造 E 编号 |
| 模型异常自然语言 | 0 | 0% | 否 | 保持 schema_failure 或显式拒绝 |

当前 8 次失败均为 schema_failure，主要集中在材料不足/未来语义案例或综合案例的 Industry 输出契约不满足。v1.0 已将其从笼统的 `llm_extraction_failed` 细分出来；失败记录同时保留 Provider 观测、输入证据数、输入字符数、延迟和最终错误。

## 3. 重试行为

Provider 最多重试 2 次，仅针对 timeout、429、5xx 和临时连接错误。此次 30 次实验没有触发可重试网络错误，因此首次成功率与重试后成功率均为 73.33%；这不是通过重试隐藏失败，schema 失败仍明确终止。

## 4. 结论

当前主要瓶颈不是网络，而是模型结构化输出在边界材料上的契约稳定性。下一步应优先做输出约束、短上下文证据包和失败回归，不应继续增加新的业务 Agent。
