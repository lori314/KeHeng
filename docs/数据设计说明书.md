# 科衡数据设计说明书

## 1. 文档目的

本文定义科衡的数据域、概念模型、来源与质量、权限、血缘和生命周期要求，为后续逻辑/物理数据库设计、知识库建设和数据治理提供基线。当前不绑定具体数据库或向量存储产品。

## 2. 数据设计原则

- 合法、正当、必要：仅处理获得授权且服务于明确尽调目的的数据。
- 原始与派生分离：原件、解析结果、索引、分析和报告分别保存并通过血缘关联。
- 权限贯穿：资料权限同步约束解析、检索、分析、报告和导出。
- 版本不可隐匿：修改形成新版本，不无痕覆盖正式输入与输出。
- 最小化和可删除：按用途控制字段与保留期，支持授权撤销后的处置流程。
- 质量可见：缺失、冲突、识别误差和过期状态作为数据的一部分传递。

## 3. 数据分类

| 数据域 | 示例 | 敏感性初判 | 说明 |
| --- | --- | --- | --- |
| 企业基础信息 | 名称、统一标识、行业、成立时间 | 内部/公开混合 | 公开属性仍需记录来源与时间 |
| 技术与知识产权 | 研发文档、专利、源材料、测试报告 | 可能含商业秘密 | 权限应细化至资料或章节 |
| 产业与经营 | 客户供应商、订单、市场分析 | 高敏业务数据 | 注意第三方信息与合同限制 |
| 财务与融资 | 报表、流水、负债、融资计划 | 高敏 | 需严格控制查看和导出 |
| 人员与治理 | 股东、团队履历、联系方式 | 可能含个人信息 | 最小化处理并明确合法基础 |
| AI 派生数据 | 分块、向量、摘要、分析发现 | 继承源数据敏感性 | 向量和摘要不得视为已脱敏 |
| 审计与运行数据 | 访问事件、任务日志、模型调用元数据 | 内部敏感 | 日志不得保存不必要的原文 |

最终分类分级以部署机构的数据制度和适用法规评审为准。

## 4. 数据来源与准入

候选来源包括企业主动提交资料、金融机构已授权内部资料、合法使用的公共信息和经许可的第三方数据。每个来源应登记所有者、取得方式、授权/许可、获取时间、适用用途、有效期、质量和更新频率。

数据进入系统前应完成：文件安全检测、格式与完整性检查、重复识别、授权检查、密级标注和基础质量评估。不明来源、许可不清、内容损坏或超出用途的数据应隔离，未经确认不进入正式分析。

## 5. 概念数据模型

| 实体 | 核心字段（概念级） | 关系 |
| --- | --- | --- |
| Organization | 机构标识、名称、策略域 | 拥有用户与尽调任务 |
| User/Role | 用户标识、角色、组织、状态 | 通过授权访问任务和资料 |
| Enterprise | 企业标识、名称、外部标识、行业 | 被多个尽调任务引用 |
| DueDiligenceTask | 任务标识、场景、状态、负责人、权限域 | 聚合资料、运行和报告 |
| SourceDocument | 资料标识、版本、来源、哈希、密级、授权、状态 | 产生解析结果和证据片段 |
| ParsedArtifact | 解析版本、类型、位置映射、质量 | 派生证据片段 |
| EvidenceChunk | 片段标识、原文、位置、元数据、权限 | 被检索并支持发现项 |
| AnalysisRun | 运行标识、输入快照、模型/提示词/工具版本、状态 | 产生分析发现 |
| AnalysisFinding | 主题、类型、内容、引用、不确定性、复核状态 | 输入评价和报告 |
| IndicatorVersion | 指标、量表、适用范围、审批状态 | 与权重集组成评价配置 |
| EvaluationResult | 指标结果、解释、引用、配置版本 | 被报告引用 |
| ReportVersion | 模板版本、章节、状态、审批、输出物 | 属于尽调任务 |
| AuditEvent | 主体、动作、对象、时间、结果、关联标识 | 覆盖关键对象操作 |

主键建议使用不暴露业务含义的稳定标识；企业统一标识等自然键作为受约束属性管理。时间字段需明确时区和事件时间/处理时间语义。

## 6. 文档与知识数据

原始文件保存不可变版本和内容哈希；解析产物保留解析器、参数、开始/完成时间、质量状态及到原文的坐标映射。知识分块应保留相邻关系、章节层级、表格结构和来源权限。向量记录关联嵌入模型与版本，模型变化时以新索引版本重建，不原地混用不可比向量。

索引按组织和任务/企业隔离。检索返回时再次验证访问权限与资料状态。资料删除或授权撤销需触发原件、派生内容、缓存和索引的协同处置，并保留满足制度要求的处置审计。

## 7. 分析与评价数据

分析发现应结构化保存事实/推断类型、主题、结论、正反证据、理由摘要、不确定性、模型和提示词版本、人工复核状态。不得只保存最终自然语言报告而丢失中间证据关系。

评价结果应保存指标与权重版本、输入值、缺失/异常处理、计算结果、风险项、解释和复核记录。小数精度、单位、币种、会计期间及口径必须明确，避免字符串或浮点默认行为造成不可追溯差异。

## 8. 数据质量规则

数据质量至少从完整性、准确性、一致性、唯一性、及时性、可解析性和可追溯性衡量。示例规则包括：

- 文件哈希相同但元数据不同的资料标记为潜在重复，不直接删除。
- 财务数值必须携带币种、单位、期间和来源位置。
- 同一事实在不同资料中冲突时保留各版本并生成冲突状态。
- OCR 低置信字段不得直接进入正式计算。
- 过期或撤销授权的证据不得用于新的分析运行。
- 引用指向的资料版本和位置必须存在且对当前用户可访问。

规则阈值、责任人和修复流程需在样本分析后补充。

## 9. 权限与安全

建议采用组织、任务、角色和资料标签组合授权。派生数据继承最严格的源数据权限；跨来源聚合不得降低密级。生产数据加密存储和传输，密钥与数据分离管理。批量导出、配置变更、权限授予和高敏资料访问属于重点审计动作。

开发和测试环境不得复制未脱敏生产数据。测试样本需标记为合成、脱敏或公开，并保存处理责任和使用限制。日志只记录必要元数据，敏感字段进行掩码或不可逆摘要。

v0.5.5 的 `data/evaluation_cases/` 全部为完全合成数据。每个案例固定保存 `company_profile.pdf`、`expected_indicators.json`、`expected_evidence.json` 和 `README.md`：PDF 是输入制品，两个 JSON 是版本化金标准，README 记录案例目的与使用边界。E 编号由运行时动态分配，因此金标准使用页码、原文短语和案例标识验证证据，不把某次运行的 E 编号固化为数据事实。

v0.9 新增 `data/real_cases/<company_id>/` 公开企业案例目录。`manifest.json` 记录企业名称、行业、文件、官方来源、发布时间、获取时间、文件类型、用途、下载状态和内容哈希；原始 PDF 放在 `sources/`，无法稳定取得的资料必须在 manifest 中明确标记而不能以合成资料替代。真实 LLM 运行产物保存在 `runtime/real_cases/<company_id>/`，包括 Technology/Industry 分析、两域评价、综合评价和报告，并附不含密钥的运行元数据。`docs/人工复核说明.md` 与 `data/real_cases/review_template.csv` 定义合理性、证据支持、过度推断、TRL 和报告可读性的人工复核接口。运行时目录包含外部模型响应和派生索引，不应提交到 Git。

v1.0 在真实案例运行元数据中固定保存 `assessment_status`、两域分数、Overall Score、`evidence_coverage`、模型、提示词版本、延迟、错误类别和证据引用。`data/real_cases/human_review_v10.csv` 由系统自动生成，人工评价列保持空白，禁止将模型自评冒充专家复核。实验原始运行记录明确区分 All Runs 与 Successful Runs Only，失败样本不从数据集中删除。

## 10. 生命周期与备份

数据状态建议包括接收、隔离、有效、失效、归档、待删除和已删除。各数据域的保留期、法律保留、删除审批、备份清理和审计留存由机构政策确定。报告发布后相关输入快照需按制度保留，以支持追溯；这不意味着可以无限期保留全部原文。

备份应覆盖关键元数据、配置和正式报告，并定期验证恢复。向量索引等可再生产物可采用与权威数据不同的备份策略，但必须具备受控重建流程。

## 11. 数据迁移与版本演进

模式变更使用可审查、可回滚或可前向修复的迁移；重要字段语义变化不得只改名称。知识索引、指标、权重和报告模板分别版本化。迁移前后验证记录数、关键约束、引用完整性和权限一致性。

## 12. 待确认事项

- 数据驻留、跨境/出域限制和机构分类分级标准。
- 首批资料类型、规模、质量分布及更新机制。
- 数据库、对象存储、搜索/向量存储和密钥管理方案。
- 财务口径、行业标准编码和外部实体对齐策略。
- 各类数据保留期限、删除证明与备份清理要求。

## v1.1 实验观测字段

真实模型实验记录 JSON mode 开关、输入证据数量、响应长度、首轮契约状态、一次修复状态和最终状态；API Key 只从环境或本地忽略文件读取，不写入实验记录。修复轮只用于结构化格式，不覆盖金标准或评分结果。

## Iteration 03 产品任务与模型交互数据

上传任务响应新增 `request_mode`、模块结果/失败类别、`result_status` 与 `run_info`。运行指纹记录输入 PDF SHA-256、检索配置、评分/提示词/源码文件 SHA-256；没有 Git commit 时 `git_commit` 为 `null`。真实模型模式的 `model_io` 暂存最终实际发出的 chunk/prompt、原始供应商响应及 token/延迟/请求失败观测，内容源自企业 PDF，按敏感派生数据管理。API Key 不属于响应字段。当前这些内容跟随单进程内存任务状态提供查询，不形成稳定审计存档；离线配对实验将结果写入新的 `runtime/review/paired_model/run-*`，runtime 被 `.gitignore` 排除。运行重启后任务状态不保证保留，不能将这一实现当作长期存储或生产留痕。
