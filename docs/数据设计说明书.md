# 科衡数据设计说明书

## 1. 文档目的

本文定义科衡的数据域、概念模型、来源与质量、权限、血缘和生命周期要求，为后续逻辑/物理数据库设计、知识库建设和数据治理提供基线。当前不绑定具体数据库或向量存储产品。

## 2. 数据设计原则

- 合法、正当、必要：仅处理获得授权且服务于明确尽调目的的数据。
- 原始与派生分离：原件、解析结果、索引、分析和报告分别保存并通过血缘关联。
- 权限贯穿：资料权限同步约束解析、检索、分析、报告和导出。
- 版本不可隐匿：修改形成新版本，不无痕覆盖正式输入与输出。
- 最小化和可删除：按用途控制字段与保留期，支持授权撤销后的处置流程。
- 质量可见：缺失、冲突、识别误差和过期状态作为数据的一部分传递。

## 3. 数据分类

| 数据域 | 示例 | 敏感性初判 | 说明 |
| --- | --- | --- | --- |
| 企业基础信息 | 名称、统一标识、行业、成立时间 | 内部/公开混合 | 公开属性仍需记录来源与时间 |
| 技术与知识产权 | 研发文档、专利、源材料、测试报告 | 可能含商业秘密 | 权限应细化至资料或章节 |
| 产业与经营 | 客户供应商、订单、市场分析 | 高敏业务数据 | 注意第三方信息与合同限制 |
| 财务与融资 | 报表、流水、负债、融资计划 | 高敏 | 需严格控制查看和导出 |
| 人员与治理 | 股东、团队履历、联系方式 | 可能含个人信息 | 最小化处理并明确合法基础 |
| AI 派生数据 | 分块、向量、摘要、分析发现 | 继承源数据敏感性 | 向量和摘要不得视为已脱敏 |
| 审计与运行数据 | 访问事件、任务日志、模型调用元数据 | 内部敏感 | 日志不得保存不必要的原文 |

最终分类分级以部署机构的数据制度和适用法规评审为准。

## 4. 数据来源与准入

候选来源包括企业主动提交资料、金融机构已授权内部资料、合法使用的公共信息和经许可的第三方数据。每个来源应登记所有者、取得方式、授权/许可、获取时间、适用用途、有效期、质量和更新频率。

数据进入系统前应完成：文件安全检测、格式与完整性检查、重复识别、授权检查、密级标注和基础质量评估。不明来源、许可不清、内容损坏或超出用途的数据应隔离，未经确认不进入正式分析。

## 5. 概念数据模型

| 实体 | 核心字段（概念级） | 关系 |
| --- | --- | --- |
| Organization | 机构标识、名称、策略域 | 拥有用户与尽调任务 |
| User/Role | 用户标识、角色、组织、状态 | 通过授权访问任务和资料 |
| Enterprise | 企业标识、名称、外部标识、行业 | 被多个尽调任务引用 |
| DueDiligenceTask | 任务标识、场景、状态、负责人、权限域 | 聚合资料、运行和报告 |
| SourceDocument | 资料标识、版本、来源、哈希、密级、授权、状态 | 产生解析结果和证据片段 |
| ParsedArtifact | 解析版本、类型、位置映射、质量 | 派生证据片段 |
| EvidenceChunk | 片段标识、原文、位置、元数据、权限 | 被检索并支持发现项 |
| AnalysisRun | 运行标识、输入快照、模型/提示词/工具版本、状态 | 产生分析发现 |
| AnalysisFinding | 主题、类型、内容、引用、不确定性、复核状态 | 输入评价和报告 |
| IndicatorVersion | 指标、量表、适用范围、审批状态 | 与权重集组成评价配置 |
| EvaluationResult | 指标结果、解释、引用、配置版本 | 被报告引用 |
| ReportVersion | 模板版本、章节、状态、审批、输出物 | 属于尽调任务 |
| AuditEvent | 主体、动作、对象、时间、结果、关联标识 | 覆盖关键对象操作 |

主键建议使用不暴露业务含义的稳定标识；企业统一标识等自然键作为受约束属性管理。时间字段需明确时区和事件时间/处理时间语义。

## 6. 文档与知识数据

原始文件保存不可变版本和内容哈希；解析产物保留解析器、参数、开始/完成时间、质量状态及到原文的坐标映射。知识分块应保留相邻关系、章节层级、表格结构和来源权限。向量记录关联嵌入模型与版本，模型变化时以新索引版本重建，不原地混用不可比向量。

索引按组织和任务/企业隔离。检索返回时再次验证访问权限与资料状态。资料删除或授权撤销需触发原件、派生内容、缓存和索引的协同处置，并保留满足制度要求的处置审计。

## 7. 分析与评价数据

分析发现应结构化保存事实/推断类型、主题、结论、正反证据、理由摘要、不确定性、模型和提示词版本、人工复核状态。不得只保存最终自然语言报告而丢失中间证据关系。

评价结果应保存指标与权重版本、输入值、缺失/异常处理、计算结果、风险项、解释和复核记录。小数精度、单位、币种、会计期间及口径必须明确，避免字符串或浮点默认行为造成不可追溯差异。

## 8. 数据质量规则

数据质量至少从完整性、准确性、一致性、唯一性、及时性、可解析性和可追溯性衡量。示例规则包括：

- 文件哈希相同但元数据不同的资料标记为潜在重复，不直接删除。
- 财务数值必须携带币种、单位、期间和来源位置。
- 同一事实在不同资料中冲突时保留各版本并生成冲突状态。
- OCR 低置信字段不得直接进入正式计算。
- 过期或撤销授权的证据不得用于新的分析运行。
- 引用指向的资料版本和位置必须存在且对当前用户可访问。

规则阈值、责任人和修复流程需在样本分析后补充。

## 9. 权限与安全

建议采用组织、任务、角色和资料标签组合授权。派生数据继承最严格的源数据权限；跨来源聚合不得降低密级。生产数据加密存储和传输，密钥与数据分离管理。批量导出、配置变更、权限授予和高敏资料访问属于重点审计动作。

开发和测试环境不得复制未脱敏生产数据。测试样本需标记为合成、脱敏或公开，并保存处理责任和使用限制。日志只记录必要元数据，敏感字段进行掩码或不可逆摘要。

v0.5.5 的 `data/evaluation_cases/` 全部为完全合成数据。每个案例固定保存 `company_profile.pdf`、`expected_indicators.json`、`expected_evidence.json` 和 `README.md`：PDF 是输入制品，两个 JSON 是版本化金标准，README 记录案例目的与使用边界。E 编号由运行时动态分配，因此金标准使用页码、原文短语和案例标识验证证据，不把某次运行的 E 编号固化为数据事实。

v0.9 新增 `data/real_cases/<company_id>/` 公开企业案例目录。`manifest.json` 记录企业名称、行业、文件、官方来源、发布时间、获取时间、文件类型、用途、下载状态和内容哈希；原始 PDF 放在 `sources/`，无法稳定取得的资料必须在 manifest 中明确标记而不能以合成资料替代。真实 LLM 运行产物保存在 `runtime/real_cases/<company_id>/`，包括 Technology/Industry 分析、两域评价、综合评价和报告，并附不含密钥的运行元数据。`docs/人工复核说明.md` 与 `data/real_cases/review_template.csv` 定义合理性、证据支持、过度推断、TRL 和报告可读性的人工复核接口。运行时目录包含外部模型响应和派生索引，不应提交到 Git。

v1.0 在真实案例运行元数据中固定保存 `assessment_status`、两域分数、Overall Score、`evidence_coverage`、模型、提示词版本、延迟、错误类别和证据引用。`data/real_cases/human_review_v10.csv` 由系统自动生成，人工评价列保持空白，禁止将模型自评冒充专家复核。实验原始运行记录明确区分 All Runs 与 Successful Runs Only，失败样本不从数据集中删除。

## 10. 生命周期与备份

数据状态建议包括接收、隔离、有效、失效、归档、待删除和已删除。各数据域的保留期、法律保留、删除审批、备份清理和审计留存由机构政策确定。报告发布后相关输入快照需按制度保留，以支持追溯；这不意味着可以无限期保留全部原文。

备份应覆盖关键元数据、配置和正式报告，并定期验证恢复。向量索引等可再生产物可采用与权威数据不同的备份策略，但必须具备受控重建流程。

## 11. 数据迁移与版本演进

模式变更使用可审查、可回滚或可前向修复的迁移；重要字段语义变化不得只改名称。知识索引、指标、权重和报告模板分别版本化。迁移前后验证记录数、关键约束、引用完整性和权限一致性。

## 12. 待确认事项

- 数据驻留、跨境/出域限制和机构分类分级标准。
- 首批资料类型、规模、质量分布及更新机制。
- 数据库、对象存储、搜索/向量存储和密钥管理方案。
- 财务口径、行业标准编码和外部实体对齐策略。
- 各类数据保留期限、删除证明与备份清理要求。

## Iteration 03 产品任务与模型交互数据

上传任务响应新增 `request_mode`、模块结果/失败类别、`result_status` 与 `run_info`。运行指纹记录输入 PDF SHA-256、检索配置、评分/提示词/源码文件 SHA-256；没有 Git commit 时 `git_commit` 为 `null`。真实模型模式的 `model_io` 暂存最终实际发出的 chunk/prompt、原始供应商响应及 token/延迟/请求失败观测，内容源自企业 PDF，按敏感派生数据管理。API Key 不属于响应字段。当前这些内容跟随单进程内存任务状态提供查询，不形成稳定审计存档；离线配对实验将结果写入新的 `runtime/review/paired_model/run-*`，runtime 被 `.gitignore` 排除。运行重启后任务状态不保证保留，不能将这一实现当作长期存储或生产留痕。

## V2 Knowledge Contract（第一、二阶段）

`backend/app/knowledge/contracts.py` 定义 Company、Source、SourceVersion、Citation、CitationLocator 和 KnowledgeChunk 的统一数据契约。`backend/app/knowledge/identity.py` 依据外部 ID、规范 URL 或上传文件 SHA-256 生成稳定 source identity，并依据内容 SHA-256 生成 source version；chunk 与 citation ID 由版本、定位信息和规范化文本确定。URL identity 保留 query 参数，只去除 fragment、主机名大小写差异、默认端口和末尾斜线差异。

- **Company** 表示企业实体；仅有 `canonical_name` 即合法。`company_id` 可为空，`resolution_status` 可取 `unresolved`、`resolved`、`ambiguous`，本阶段不执行实体消歧。
- **Source** 是原始来源本身，包含稳定 `source_id`、来源类型、标题、可选 `canonical_url`、发布者、外部 ID 和扩展 metadata，不要求本机 `local_path`。契约为兼容已有数据保留可选时间与内容 SHA-256 字段；V2 研究网页的抓取时间、发布日与正文 hash 写入 SourceVersion，provider 标识写入 Source metadata 和 SourceVersion metadata。
- **Citation** 表示某个 Source 的具体出处位置，具有独立 `citation_id`、`source_id`、来源标题、摘录和可选 URL。`CitationLocator` 可保存 PDF 页码及原 locator 文本，也可保存网页 URL、section/heading、paragraph number 和 text anchor。
- **KnowledgeChunk** 是带 `source_id`、`source_version_id` 和 Citation 的统一知识单元，并可携带 `company_id`、`knowledge_layer`、domain/template tags、事件信息、实体和扩展 metadata。知识层预留 enterprise、domain、lifecycle、standard、regulation、financial_rule、general；标签和事件类型保持开放字符串，不在本阶段硬编码行业分类。
- `task_id` 是当前分析/上传范围标识，不是长期知识身份。PDF adapter 将它放入 `KnowledgeChunk.metadata` 以兼容旧流程。`legacy_chunk_id` 只记录旧任务级 chunk 标识；V2 `chunk_id` 由 source version、页码/定位器和文本生成，跨任务重导入时保持稳定。
- `E1/E2` 等编号仍可用于当前一次 Agent 上下文中引用检验，但只是临时编号；长期引用应以 Citation 的 `citation_id` / `source_id` 和位置定位，不能依赖 E 编号。

`backend/app/knowledge/adapters.py` 提供 `parsed_document_to_source` 和 `document_chunk_to_knowledge_chunk`。前者保留 document_id、document_name、task_id、源文件哈希及解析元数据，不复制 machine-local `local_path`；后者保留原 chunk_id 为 `legacy_chunk_id`、并保留原文、PDF page_number 和 locator，将 document_id、task_id、source SHA-256 放入扩展 metadata，生成由 source version、位置和规范化原文决定的稳定 V2 chunk/citation ID。转换可回到 PDF 页和原始摘录。

第二阶段新增 `backend/app/knowledge/repository.py` 与 `shared_knowledge_base.py`：SQLite 是共享知识的权威存储，保存 company、source、source version、完整 KnowledgeChunk/Citation 和版本历史；Chroma 是可重建的当前版本向量索引，只保存检索所需 metadata、文本和 embedding。重复导入相同 source/content 复用版本和 chunk ID；新内容形成新版本，旧版本及 chunk 保留在 SQLite 并从当前向量检索中排除。检索支持 company、knowledge layer 和 source type metadata filter，返回前再从 SQLite 读取完整来源与 citation。默认数据目录为 `runtime/knowledge/`，属于运行时数据，不应提交到版本库。

PDF adapter 已接入稳定身份和版本字段，但原 `DocumentSource → DocumentChunk → RetrievedEvidence → Agent Evidence → ReportEvidence` 分析主链路仍使用任务隔离 Chroma，没有迁移到共享知识库。第二阶段时共享知识库尚无联网采集；第三阶段的当前实现及来源数据字段见下文。知识更新 UI 仍未实现。

### V2 第三阶段：外部研究来源

`backend/app/research/` 将 Tavily 搜索记录转换为 `Source → SourceVersion → KnowledgeChunk/Citation`。URL 经保守 canonicalization 后作为 logical source identity；SourceVersion 内容哈希针对清理换行后的正文计算 SHA-256，版本保存 `retrieved_at`、`published_at`、provider 与 `content_scope`。Source 保存 title、canonical URL 和 provider；SourceVersion 保留每次正文状态。旧版本到达时间早于 current 时仍可写入历史，但不覆盖 current，也不更新逻辑 Source 的当前标题或 Shared Chroma 索引。

## V2 企业身份与外部来源准入字段补充

`backend/app/research/entity_resolution.py` 定义严格结构化的主体解析结果：状态、输入名称、规范名称、别名、官网、统一社会信用代码、解析证据 URL、候选主体和原因。解析证据 URL 必须来自当前身份检索结果；已解析实体的名称/别名与代码须能在引用内容中找到，官网须来自结果 host 或结果正文中的显式 URL。成功结果写回既有 `Company`，不改变稳定 `company_id`；`Company.metadata` 增加 `resolution_evidence_urls`、`resolved_at` 和 `resolver_version`。歧义候选带各自证据 URL；歧义/未解析状态不写入搜索页面。

每页的 `SourceRelevanceDecision` 记录 `status`（relevant / irrelevant / uncertain）、URL、页面证据片段和判定原因。身份解析未成功时没有页面准入；解析成功后只有 relevant 页面可产生 Source、SourceVersion、KnowledgeChunk 和 Citation。迭代结果与 `ResearchTraceEntry` 保存 relevant、irrelevant、uncertain 数量及按来源类型统计的准入数量；没有新增独立持久化的 gate 决策表。`backend/app/research/source_classifier.py` 根据来源 host 注册表及搜索 topic 得到现有 `SourceType`，配置位于 `configs/research/source_host_registry.yaml`；`source-hosts.v1` 随 Source、SourceVersion 和 KnowledgeChunk metadata 一并保存。当前 source URL 主要表达网页来源；该分类不等于专利、论文或登记记录的专用结构化连接器。

网页正文按 Markdown heading 与段落边界分块，默认目标上限 1,400 字符、相邻分块最多重叠 160 字符。Citation locator 保留 URL、section/heading、段落序号和稳定段落 anchor。全文 hash 用于版本去重；chunk ID 仍由 version、locator 和规范化 chunk 文本确定。只有 Tavily `raw_content` 达到正文阈值或 Extract 返回正文时标记 `content_scope=full_content`；只有搜索摘要时标记 `search_snippet`，此标记同时写入 Source metadata、SourceVersion metadata 和 KnowledgeChunk metadata，后续消费方应将它与完整正文证据区别处理。

企业实体最初以 NFKC 规范化、大小写折叠后的企业名确定本地稳定 ID，并默认 unresolved；V2 第六阶段增加了基于本轮身份检索证据的显式解析状态与 Company 更新，不能把名称派生 ID 本身当作工商消歧结果。来源类型最初仅区分 web、政府域和 news topic；第六阶段改由 `source_classifier.py` 与 host registry 分类，并在官网身份已核验后识别企业官网。Trace 写入 `runtime/research/`，SQLite/Chroma 数据写入 `runtime/knowledge/`；两者均为运行数据且 Git 忽略。Tavily 与 Planner LLM 的调用密钥只从后端环境读取，不进入以上持久化结构。

### V2 第四阶段：科技语义派生数据

科技语义注册表放在 `configs/knowledge/`，分别维护领域、六种可组合模板和标准 reference metadata 版本。标准 reference 仅含标准编号、名称、范围、状态说明、来源链接与使用边界；标准原文尚未合法进入知识库，因此这些登记不产生原文 Citation，也不得被解释为标准条文。

`TechnologyDomainProfile` 保存 primary/secondary domain IDs、分类证据 chunk IDs、理由和 registry 版本。`TechnologyTemplateSelection` 保存所选模板 ID、每个模板的证据 chunk IDs 与理由。`TechnologyFact` 保存稳定 fact ID、company、subject/predicate/object、开放字符串 fact_type、可选事件时间与量值、唯一来源 chunk ID、从原 chunk 复制的 Citation、domain/template tags、定性来源质量类别和 processor 版本。模型返回的 source chunk ID 必须属于本次输入当前 GENERAL chunk 集合；否则该 fact 被丢弃并记录处理警告。跨来源综合 fact 不在此阶段生成。

来源质量类别由确定性 SourceType 与 `content_scope` 得出：`authoritative_public_record`、`first_party`、`academic_or_patent`、`third_party`、`weak_web`、`snippet_only`。其中 snippet 固定为最低等级，不使用伪精度浮点置信度。

派生 `KnowledgeChunk` 不覆盖原始 GENERAL chunk：通用企业事实进入 `enterprise`，落在模板 milestone 类型列表内的 fact type 进入 `lifecycle`。派生 chunk 与 fact 共用原 SourceVersion 和 Citation，metadata 明确记录 `semantic_kind=technology_fact`、`derived_from_chunk_id`、`fact_id`、`processor_version` 及 fact payload；派生文字同时声明其为模型抽取、需回看引用核验。原始 Source/SourceVersion 历史不改写。

SQLite 知识库 schema v2 增加 `technology_semantic_profiles` 表，按 company、processor version、template registry version 保存/更新 Profile JSON；repository 可重新加载最新或指定版本。fact ID 和 derived chunk ID 对相同原始 chunk 与版本配置保持稳定，重复处理可幂等重写。知识库检索索引只增添新的派生知识向量，并通过 SQLite 回填原 URL、标题、摘录和定位。

语义 Profile JSON 及运行目录中的 CLI 输出包含企业事实、原文 Citation 和处理结果，按企业敏感派生数据管理；SQLite 与 `runtime/technology_semantic/` 属运行数据，不提交 Git。显式调用语义 CLI 时，当前 GENERAL 文本、来源 Citation 和结构化阶段输出会发送给环境配置的 LLM 服务；调用前应满足部署方数据出域政策。密钥只从既有环境变量注入，不写入 Profile。
### V2 第五阶段：金融事实与联合推理数据

`FinancialFact` 与 `TechnologyFact` 对称，包含稳定 fact ID、company、subject/predicate/object、fact_type、期间/事件时间、数值/单位/币种、唯一 `source_chunk_id`、原 Citation、`SourceQuality`、financial dimension 和 processor version。允许从 GENERAL 和 ENTERPRISE 的当前 chunk 抽取；chunk 不在本轮输入则拒绝，citation 从原始 chunk 复制，因此 URL、网页段落或 PDF 页码沿用原始 locator。一个 fact 只引用一个来源，不允许跨来源合并。

`configs/finance/finance_registry.yaml` 内含四类标准字段：生命周期金融服务、创新积分制2.0信息维度、科技金融场景以及流动资金贷款尽调字段；另有适用于六个科技模板的规则及来源 metadata。Registry 中政策摘要/来源链接用于规则治理和场景边界，不是知识库 Citation，也不应冒充条文原文。创新积分标准维度不形成官方积分总分。

`TechFinanceProfile` 以 `technology_profile_id` 关联科技 profile，分别保留 technology_stage 与 enterprise_lifecycle；当前企业生命周期固定为 `unknown`，不会从技术阶段推定。融资活动、风险关注、监测节点的 `EvidenceBundle` 包含 technology fact IDs、milestone refs、financial fact IDs 和 rule IDs。程序检查各引用都存在且 rule/scenario 在 registry 内。未披露维度进入 `FinancialInformationGap`，缺失不是负面事实。Finance profile 的稳定 ID 由企业、科技 profile、processor/registry 版本和 FinancialFact IDs 确定。

SQLite schema v3 新增 `technology_finance_profiles`，唯一版本键为 company、technology profile ID、processor version、finance registry version。该 JSON 是企业敏感派生数据，落在本地运行数据库，需按业务部署保留和访问策略管理。系统不生成授信审批、额度、信用/偿债评级或合并风险分。
