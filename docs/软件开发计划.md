# 科衡软件开发计划

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 初稿，待项目组评审 |
| 适用阶段 | 项目启动至首个可验收版本 |
| 规划方式 | 里程碑驱动、迭代交付 |
| 更新原则 | 里程碑、范围、资源或主要风险变化时更新 |

## 2. 项目概述

科衡面向科技型企业融资尽调场景，目标是以多模态资料治理、RAG、专业智能体和多指标评价为基础，形成带证据、可解释、可人工复核的企业价值与风险分析。项目不以快速演示为主要目标，而以建立可靠的工程、数据与模型治理基础为先。

## 3. 建设目标与范围

首个可验收版本拟覆盖单个企业尽调任务的资料导入、资料解析、证据检索、专项分析、结构化评价、报告生成和人工审阅闭环。系统应能够指出证据来源、信息缺口和不确定性，并记录关键版本。

首阶段不包括自动授信或投资决策、大规模实时舆情平台、未经授权的外部数据抓取、全行业统一评价标准以及无人审核的报告对外发布。具体范围以《需求规格说明书》评审结果为准。

## 4. 开发策略

- 先确定业务流程、数据边界和验收标准，再选择框架与模型。
- 先打通小规模、可观测、可回归的端到端链路，再扩展资料类型与智能体数量。
- 规则、提示词、指标、权重和模型均版本化，支持重放和对比。
- 研发环境只使用合成或脱敏数据；生产数据接入须经过安全与合规评审。
- 每个里程碑以可验证成果和退出条件收口，不以代码量作为完成标准。

## 5. 阶段与里程碑

| 阶段 | 主要工作 | 主要交付物 | 退出条件 |
| --- | --- | --- | --- |
| M0 项目启动 | 明确角色、范围、术语、风险与协作规则 | 工程文档初稿、仓库规范 | 文档完成首次评审，重大分歧有负责人 |
| M1 需求与样本基线 | 访谈用户、梳理流程、准备脱敏样本与金标准 | 需求基线、用例、数据清单、验收指标 | 核心用例与边界获业务和合规确认 |
| M2 架构与技术验证 | 完成关键选型，对解析、检索、模型输出做小规模验证 | 架构决策记录、接口草案、验证报告 | 关键风险有验证证据及备选方案 |
| M3 最小闭环 | 建设单企业、有限文档类型的端到端工作流 | 可部署的最小系统、测试与使用说明 | 核心流程可运行，证据引用可核验 |
| M4 能力增强 | 扩展多模态、专项 Agent、评价模型与审阅能力 | 增强版本、模型卡、回归评测集 | 质量门禁满足约定，风险可接受 |
| M5 试点与验收 | 受控试点、性能与安全验证、用户培训 | 验收报告、运维手册、项目总结 | 验收问题闭环并完成发布审批 |

各阶段工期需在团队规模、数据可用性和部署约束明确后估算，当前不提供缺乏依据的日期承诺。

## 6. 工作分解

1. 产品与业务：用户角色、尽调流程、报告模板、指标定义、验收口径。
2. 数据工程：资料清单、解析质量、元数据、脱敏、权限、生命周期。
3. AI 与评价：检索策略、Agent 契约、提示词治理、指标权重、离线评测。
4. 应用工程：前后端、任务编排、接口、审计、部署与可观测性。
5. 质量与安全：测试自动化、威胁建模、权限验证、红队测试、发布门禁。
6. 项目治理：里程碑、风险、变更、决策记录和跨角色评审。

## 7. 角色与职责建议

| 角色 | 核心职责 |
| --- | --- |
| 产品/业务负责人 | 确认场景、优先级、报告口径和验收结果 |
| 科技金融/风控专家 | 审核指标、权重、风险规则和使用边界 |
| 架构与应用研发 | 架构、接口、实现、部署与工程质量 |
| 数据/AI 工程师 | 文档处理、检索、模型、Agent 与评测 |
| 测试与安全人员 | 测试策略、安全审查和质量门禁 |
| 数据责任人 | 数据授权、分类分级、访问与销毁审批 |

关键规则与模型变更应至少由业务、技术和风险/合规三个视角共同评审。

## 8. 质量管理

需求应具备可验证验收条件；架构决策记录背景、选择与后果；代码合并前完成评审和自动化检查；模型能力以固定评测集衡量；报告中的证据引用进行抽样或全量校验。缺陷按业务影响、数据风险和可恢复性分级，高严重度问题阻断发布。

建议的发布门禁包括：核心流程测试通过、无未处置的高危安全问题、引用正确性达到商定标准、关键输出可追溯、回滚方案可用、人工复核流程已验证。

## 9. 风险与应对

| 风险 | 影响 | 初步应对 |
| --- | --- | --- |
| 资料质量差或格式复杂 | 解析和结论不稳定 | 建立资料准入、质量评分和人工纠错机制 |
| 模型幻觉或错误引用 | 误导业务判断 | 证据约束、引用校验、拒答阈值和人工复核 |
| 指标权重缺乏共识 | 评分不可接受 | 专家评审、敏感性分析、分场景版本化 |
| 敏感数据泄露 | 合规与声誉损失 | 数据最小化、权限隔离、脱敏、审计与私有化评估 |
| 外部模型或组件锁定 | 成本与迁移风险 | 适配器隔离、基准测试、保留替代方案 |
| 需求持续扩张 | 延期与质量下降 | 变更控制、优先级和里程碑范围冻结 |

## 10. 变更与沟通

需求、接口、数据、指标或发布范围发生变化时，应提交变更说明，至少包含目的、影响范围、风险、迁移/回滚方案和验证方式。项目例会跟踪里程碑与风险；设计评审处理跨模块决策；发布评审确认质量与合规门禁。未决事项应记录负责人和目标决策时间。

## 11. 待确认事项

- 首批用户机构、融资产品和适用行业范围。
- 部署形态、网络隔离与数据驻留要求。
- 可合法使用的数据源、样本规模和标注资源。
- 报告模板、指标尺度、权重治理和人工审批链。
- 可接受的质量、时延、吞吐与成本目标。

## v1.1 冻结里程碑

目标是降低结构化输出失败而不改变评分和案例金标准。完成 Provider JSON mode、单次格式修复、六案例五次实验、失败企业复核和版本冻结检查；最终成功率低于 90% 时只记录原因，不扩展业务功能。
