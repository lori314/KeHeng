# 真实模型与案例实验报告（v0.9）

> 本文档是科衡 v0.9 的实验记录底稿。合成案例有固定金标准；公开企业案例没有人为制作“标准答案”，其结果仅用于验证可运行性、证据链和现实可读性，不代表企业真实融资价值。

## 1. 实验目的

验证百炼真实大模型在现有“PDF → RAG → Technology Agent → Industry Agent → Evaluation → Report”闭环中的可用性、结构化契约稳定性、证据引用完整性和否定/未来语义保护能力；同时用公开企业资料检验系统面对长文档和复杂表述时是否能运行并产出可复核材料。

## 2. 系统版本与边界

实验基于 KeHeng v0.9。Evaluation Engine、综合权重和 Report Generator 沿用现有实现：LLM 只抽取指标与证据，所有技术分、产业分和 Overall Score 仍由确定性代码计算，报告生成器不重新评分。Industry Agent 本轮仍是本地规则实现，未增加 Finance/Risk Agent、AHP、外部金融数据或前端功能。

## 3. 模型配置

| 项目 | 配置 |
| --- | --- |
| Provider | Alibaba Cloud Bailian OpenAI Compatible |
| 模型 | `qwen3.7-plus` |
| Endpoint | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| Temperature | 0 |
| Technology prompt | `v0.9-strict-json-technology-r1` |
| 调用方式 | 标准库 HTTPS transport；`response_format=json_object` |
| 密钥处理 | 仅从本地环境/未提交本地 CSV 读入内存，实验配置只记录是否已配置 |

模型选择依据是中文技术资料理解、结构化 JSON 可靠性与批量实验成本的平衡。脚本先调用 `/models` 查询账号可用模型，再确认选定模型存在。完整配置保存在 `runtime/experiments/real_llm/experiment_config.json`，不包含密钥。

## 4. 合成评测集

固定案例包括三个技术案例（明显优势、材料不足、未来/否定语义）和三个技术+产业案例（技术强产业强、技术强产业弱、技术弱产业强）。每个案例保留原 PDF 与金标准；每个案例规则模式运行 1 次，真实 LLM 模式运行 3 次。原始请求结果、模型响应、分析、评价、报告和错误记录见 `runtime/experiments/real_llm/raw_runs.json` 与同目录其他 JSON，不能只引用汇总数字。

## 5. 评价指标

| 指标 | 定义 |
| --- | --- |
| API 调用成功率 | 真实 LLM 请求完成且返回可处理结果的比例 |
| JSON 契约成功率 | 结果通过 Technology/Industry Pydantic 契约的比例 |
| 指标完整率 | 四项技术指标（综合案例另含四项产业指标）均存在的比例 |
| 有效 E 编号引用率 | 引用存在于本次检索证据集合且格式有效的比例 |
| 金标准指标匹配率 | 与固定案例期望指标在容差内一致的比例 |
| 期望证据命中率 | 报告引用命中金标准页码和原文短语的比例 |
| 评价/报告成功率 | 确定性 Evaluation 与 Report 均成功的比例 |
| 稳定性 | 3 次运行的分数 range/stddev、TRL 值集合和成功率 |

## 7. LLM 多次运行稳定性

本次 18 次真实 LLM 运行的总体结果为：API 调用成功率 55.56%，JSON 契约成功率 55.56%，指标完整率 55.56%，有效 E 引用率 55.56%，金标准指标匹配率 21.53%，期望证据命中率 51.85%，Evaluation 成功率 55.56%，Report 成功率 55.56%。`metrics.json` 的 `stability_by_case` 记录每个案例 3 次运行的成功率、技术/产业/综合分 min/max/range/stddev，以及 TRL 值和是否稳定。成功运行的综合案例在本次重复中仅各有 1 次，单次分数分别为 76.09 和 56.45，不能据此宣称低波动；材料不足案例成功运行保持未评分。TRL 字段在本组输出中没有形成可稳定抽取的 `TRL-n` 数值，因此不能宣称 TRL 判断稳定；这本身是待改进项。

## 8. Technology + Industry 综合评价

综合案例使用既有技术 60%、产业 40% 配置。该实验检验技术强/产业弱与技术弱/产业强是否能被区分，并记录两域分数和 Overall Score 波动。产业前景高不应自动推导企业竞争力高；产业证据与技术证据使用各自 E 编号空间并在报告中合并展示。

## 11. 错误案例与局限性

错误记录以 `error_cases.json` 和每个真实案例的 `run_metadata.json` 为准。本轮固定案例实际发现 10 条记录：主要是多次显式 LLM 抽取失败，以及 case_003、case_tech_high_industry_low 的未来语义/TRL 过高风险；提示词示例修正后未再出现 `[EX]` 无效标记。最新真实案例校验未发现无效引用，但 CATL 和埃斯顿的运行失败仍在各自 metadata 中保留，未用 rule 结果掩盖。当前局限包括：规则检索仍是轻量本地方案；真实公开资料的版式、页眉页脚和长文本会影响召回；Industry Agent 在 v1.0 记录期间尚未接入 LLM，已在 v1.1 复验中接入；没有专家复核统计；Temperature=0 也不等于输出完全确定；真实案例没有客观金标准；TRL 表达尚未统一为可自动比较的结构化字段。

## 12. 结论与论文使用边界

本实验可作为论文中的“系统实现、实验设计、误差分析和案例研究”材料。只有在报告中同时披露成功率、失败样本、证据缺口和人工复核计划后，才可将结果用于论证方法的工程可行性；不能据此宣称模型已具备真实授信、投资或融资决策能力。

# v1.0 最终实验补充

## 13. 实验设置与模型参数

v1.0 在不增加 Finance/Risk Agent、不改变技术/产业评价职责的前提下，增加 Provider 有限网络重试、请求观测、Industry LLM 模式和综合评价状态建模。主模型仍为百炼 `qwen3.7-plus`，Temperature=0；Technology 提示词为 `v0.9-strict-json-technology-r1`，Industry 提示词为 `v1.0-industry-strict-json`。网络层最多重试 2 次，仅针对 timeout、429、5xx 和临时连接错误。

## 14. 合成数据与实验次数

三个 Technology 案例和三个 Technology+Industry 综合案例保持原 PDF 与金标准不变。每案例执行 5 次 LLM 流程，共 30 次 LLM 流程；综合案例每次分别调用 Technology LLM 与 Industry LLM。Rule baseline 每案例 1 次。完整记录位于 `runtime/experiments/v10/`。

## 15. 首次成功率与重试后成功率

| 口径 | 首次成功率 | 重试后最终成功率 | JSON/schema 成功率 | Evaluation 成功率 | Report 成功率 |
|---|---:|---:|---:|---:|---:|
| All Runs | 73.33% | 73.33% | 73.33% | 73.33% | 73.33% |
| Successful Runs Only | 100% | 100% | 100% | 100% | 100% |

本轮没有触发网络可重试错误，8 次失败均为 `schema_failure`；因此重试未改变成功率。该结果说明当前主要问题是结构化输出边界稳定性，而不是 HTTP 网络层。

## 17. 综合评价状态建模

综合结果新增：

- `fully_scored`：技术和产业四项指标均有有效证据；
- `partially_scored`：两个一级维度均可评分，但部分子指标缺失；
- `insufficient_evidence`：任一一级维度整体不可评分，`overall_score=null`；
- `pipeline_failed`：LLM、RAG 或系统流程失败。

同时输出 `evidence_coverage`，例如 `technology=0.75`、`industry=1.0`、`overall=0.875`。当一级维度缺失时，综合引擎不再把剩余维度重新归一化为看似完整的 Overall Score。

## 19. 稳定性与延迟

成功综合案例的 Overall Score 波动范围：

- 技术强/产业强：约 1.26 分；
- 技术强/产业弱：约 2.44 分；
- 技术弱/产业强：因技术维度缺失，Overall 保持 null。

30 次流程的观测延迟均值约 36.34 秒，范围约 22.41--50.95 秒。每次调用还记录输入证据数、输入字符数、输出字符数和重试次数。

## 20. 失败案例与局限性

8 次结构化失败集中在边界材料和 Industry 输出契约；未来语义案例仍发现“TRL 过高”风险提示。当前没有观察到 429、5xx 或 timeout，因此网络重试机制尚未通过真实故障样本充分验证。连续评分误差仍较大，说明 LLM 指标理解不能替代人工校准。真实企业没有专家金标准，系统分数不能解释为企业真实融资价值。

## 21. 论文使用结论

v1.0 已具备参赛论文主体所需的系统实现、Rule/LLM 对比、Technology+Industry 综合评价、失败分类、状态建模和真实案例研究材料。但不建议继续堆叠新 Agent；在 LLM 成功率低于 90%、连续误差和人工复核尚未改善前，应优先完成稳定性回归、人工复核和论文撰写。

> 版本说明：本段是 v1.0 阶段结论；v1.1 已完成结构化稳定性复验并达到冻结门槛，但指标语义误差和人工复核不足仍然是论文局限。

## 22. v1.1 结构化输出稳定性复验

### 22.1 配置与方法

使用百炼 OpenAI Compatible endpoint `https://dashscope.aliyuncs.com/compatible-mode/v1` 的 `qwen3.7-plus`，temperature=0，启用 `response_format: {"type":"json_object"}`。Technology 与 Industry Prompt 版本分别为 `v1.1-structured-json-technology`、`v1.1-structured-json-industry`。首轮契约失败时最多发送一次格式修复，不调用 rule、不改变事实和评分。

### 22.2 六案例五次结果

| 指标 | v1.0 | v1.1 |
|---|---:|---:|
| 运行次数 | 30 | 30 |
| 首次结构化成功率 | 73.33% | 100.00% |
| 修复触发率 | — | 0.00% |
| 修复成功率 | — | 0.00%（无触发样本） |
| 最终结构化成功率 | 73.33% | 100.00% |
| Evaluation 成功率 | 73.33% | 100.00% |
| Report 成功率 | 73.33% | 100.00% |
| 有效证据引用率 | 73.33% | 100.00% |
| Technology 指标 MAE | 6.8958 | 7.6471 |
| Industry 指标 MAE | 8.2727 | 6.3333 |

v1.1 的 schema_failure 为 0，说明 JSON mode、精简约束和数值 confidence 约束已经消除了本轮格式失败；由于没有失败样本，repair 的真实成功率尚未得到实证。Technology/Industry 分数的跨案例范围分别为 75.25/59.00，反映案例差异而非单一案例稳定性，不能把 30 次成功等同于评分准确。

当前 LLM 输出契约没有独立 TRL 字段，30 次运行均未形成可计算的 TRL 数值序列；因此 TRL 稳定性记为“未观测”，而不是假设稳定。语义检测仍保留 5 次未来/TRL 风险提示。

### 22.3 语义风险

固定案例仍记录 5 次“未来语义或 TRL 过高”风险提示；该类问题不是 schema repair 可以解决的，应在论文中作为语义校验局限披露。金标准和 Evaluation 未修改。

### 22.4 Rule vs LLM

| 对比项 | 观察 |
|---|---|
| 结构化契约 | Rule 无模型契约；LLM v1.1 首轮 30/30 成功 |
| 证据有效率 | LLM 100%，未发现无效 E 编号或无证据确定性结论 |
| Technology 指标 | LLM MAE 7.6471，存在跨案例分数波动，不能替代规则量表校准 |
| Industry 指标 | LLM MAE 6.3333，仍需人工复核竞争位置与政策外推 |
| 评分职责 | 两种模式都由同一 Evaluation Engine 计算，LLM 未直接生成综合分 |

### 22.5 CATL 复核

宁德时代案例按 v1.1 Prompt 与 JSON mode 重跑，Technology/Industry 均首轮结构化成功，最终状态为 `insufficient_evidence`，技术、产业和综合分均为 `null`，没有把资料不足强行转成评分，也没有 rule fallback。运行记录见 `runtime/real_cases/catl/run_metadata.json`。
